# 取得先の許可リストをポート単位にする設計

Issue #482(関連: #377 / PR #480、`2026-10-10-ssrf-fetch-guard-design.md`)

## 目的

取得先の許可リスト(`FetchAllowlist`)は、登録アカウントのホストを private / loopback に解決されても取得できる例外にしている。現状はホスト部だけで照合し、ポートを区別しない。そのため `mi.home.lan:3000` で登録すると、`http://mi.home.lan:22/` や `http://mi.home.lan:8080/` のような同じホストの別ポート(同じマシンで動く別サービス)にも取得が通る。

取得は GET のみだが、`fetch_url_bytes` は応答本文を WebView へ返す。アカウントのホストが信頼できる前提なら実害は小さいが、例外が及ぶ範囲をポート単位まで狭める(ハードニング)。

成功条件:

- ポート付きで登録したアカウントのホストは、その登録ポートの URL だけが例外になる。
- ポート無しで登録したアカウントのホストは、80 と 443 の URL だけが例外になる。
- 許可リストにあるホストへの、許可外ポートの URL は送信前とリダイレクトの各ホップで拒否される(ホスト名・IP リテラルの両方)。
- 許可リストに無いホストの挙動は変わらない(ポートは見ず、リゾルバが private / loopback への解決だけを拒否する)。
- API 通信(`state.http`)と、`save_url_to_file` / `fetch_url_bytes` 以外のコマンドには影響しない。

## 前提(コードの現状)

- `FetchAllowlist` の中身は `Arc<RwLock<HashSet<String>>>`。キーは `host_key()` が出すホスト部(小文字化・punycode 化・ポートと末尾ドットを除く)。
- `reqwest` の DNS リゾルバ(`GuardedResolver`)にはホスト名しか渡らず、ポートは見えない。許可リストにあるホスト名なら `filter_addrs` が全アドレスを通す。したがって「許可ホスト + 許可外ポート」はリゾルバでは止められず、URL 全体が見える `validate_url`(送信前とリダイレクトの各ホップで呼ばれる)で止める。
- API クライアントは `https://{host}/api` 固定なので、ポート無しのアカウントのホストは 443 に接続している。

## 設計

### 1. `FetchAllowlist`

- 内部を `HashMap<String, HashSet<u16>>`(`host_key` → 許可ポート集合)にする。
- `replace(hosts)` のシグネチャは変えない(アカウントのホスト文字列の列を受ける)。`state.rs` の呼び出し側(`AppState::new`、`refresh_fetch_allowlist`)は変更しない。
- 各ホスト文字列から `host_key` とポートを取り出して格納する。
  - ポート付き(`mi.home.lan:3000`): `{3000}`
  - ポート無し(`mi.home.lan`、IP 直指定の `192.168.1.10` も同様): `{80, 443}`
  - 同じ `host_key` が複数あれば、ポート集合の和集合にする。
  - ポートが数値として解釈できない(`host:99999` など)エントリは無効にし、格納しない(許可しない側に倒す)。そのホストでは API にも接続できないため実害はない。
- メソッド:
  - `contains_host(key)`: ホストが許可リストにあるか。`GuardedResolver` / `filter_addrs` が使う(従来の `contains_key` に相当。リゾルバにはポートが渡らない)。
  - `allows(key, port)`: ホストが許可リストにあり、かつ `port` がその集合に含まれるか。`validate_url` が使う。
- ポートの取り出しは、現行の `host_key` と同じ規則(最後の `:` 以降が数字だけならポート)を共有して、`host_key` とポート抽出で食い違わないようにする。

### 2. `validate_url`

URL のポートは `url.port_or_known_default()`(`http` は 80、`https` は 443)で取る。

- ホストが IP リテラルの場合:
  - `is_blocked_ip` に該当しなければ、従来どおり許可。
  - 該当する場合は、`allows(ip.to_string(), port)` が真のときだけ許可する(従来は `contains_key`)。
- ホストがドメイン名の場合:
  - `host_key` が `contains_host` で許可リストにあるのに `allows(key, port)` が偽なら拒否する。
  - 許可リストに無いホストは、従来どおり通す(接続時にリゾルバが検証する)。
- どちらの拒否も `BlockedAddress` を返す。ユーザー向けのメッセージは変えない(`取得先が許可されていません(ローカル/社内ネットワークのアドレス)`)。
- リダイレクトポリシーは各ホップで `validate_url` を呼んでいるので、変更しない。

スキームとポートの組み合わせ(`http` なのに 443 など)は検査しない。

### 3. 副作用と割り切り

- アカウントのホストと同じホスト名で、登録ポート(ポート無しなら 80/443)以外にあるメディアサーバー(同じホスト名の `:9000` の MinIO など)は、公開 IP に解決される場合でも拒否される。リゾルバがポートを見られないため、許可ホストの条件をポートだけで分けられないことによる。
- 外部のメディアサーバー(許可リストに無いホスト)はポートの規則を受けない。
- 影響を受けるのは `save_url_to_file` と `fetch_url_bytes` だけ。

### 4. テスト

- `net_guard.rs` の単体テスト:
  - ポート付き登録で、登録ポートの URL が通り、他のポートが拒否される。
  - ポート無し登録で、80 / 443(`http://host/` と `https://host/`)が通り、他のポートが拒否される。
  - 同じホストの複数登録でポート集合が和集合になる。
  - IP リテラル(`192.168.1.10:3000` を登録)で、登録ポートが通り他のポートが拒否される。
  - 数値でないポートのエントリが無効になる。
  - リダイレクトで許可外ポートへ飛ばされると拒否される(wiremock)。
  - 許可リストに無い公開ホストは、任意のポートでも `validate_url` を通る。
- 既存テストの修正:
  - `allow.replace(["localhost"])` は `MockServer` のランダムポートに届かなくなるので、`localhost:{port}` の形で登録する(`net_guard.rs` の wiremock テスト、`commands/note.rs` の `allow_localhost` と周辺)。
  - `contains_key` を使う箇所(`net_guard.rs` の `allowlist_replace_swaps_the_whole_set`、`state.rs` の `refresh_fetch_allowlist_follows_registered_accounts`)は `contains_host` / `allows` に合わせる。
- `cargo test`(`cd src-tauri`)で確認する。

### 5. 仕様書の更新

`2026-10-10-ssrf-fetch-guard-design.md` を、実装と同じ PR で次のように直す。

- §2「許可リスト」: 型を「ホスト → 許可ポート集合」に変え、照合キーとポートの規則(ポート付きはそのポート、ポート無しは 80/443)を書く。IP リテラルの照合も「キーと完全一致」から「ホストとポートの一致」に直す。
- §1 の `validate_url` の説明: ドメイン名の URL も、許可ホストならポートを検査すると追記する。
- 「既知の限界」: 同じホスト名の別ポートにあるメディアサーバーは拒否される、と追記する。
