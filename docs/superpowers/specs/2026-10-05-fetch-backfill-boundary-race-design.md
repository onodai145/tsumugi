# fetch_backfill の境界延長の競合と、update_column の失敗順序 設計 (Issue #456 P5)

#446 / PR #451(カラムごとの世代フェンス)の最終レビューで残った、変更前からの2点を直す。どちらも `src-tauri/src/commands/column.rs` の中で閉じる。

1. `fetch_backfill` が、ロックの外で読んだ境界から延長計画(`plan_boundary_extend`)を作るので、同じ世代の別の書き込み(並行するギャップ埋めの境界の引き上げ)と交錯して、境界を「完全」と誤って広げうる。
2. `update_column` が、`invalidate`(新しい定義の保存・ストリームのクローズ・キャッシュの破棄)の後で失敗すると、ストリームが閉じたままになる。

## 背景・原因

### 1. 延長計画が、ロックの外の古い境界から作られている

境界(`column_source_boundary`)は、「この境界より新しい範囲は、キャッシュが完全に持っている」という主張。`fetch_backfill` は次の順に動く。

1. 世代を控え、ロックの外で境界を読む(`boundaries`)。
2. キャッシュ提供の判断をする(読み取りだけ)。
3. API から取得する(ネットワーク)。
4. 取得後に、手順1の `boundaries` から延長計画 `plan_boundary_extend(&boundaries, until_id, outcomes)` を作る。ソースごとに「既存の境界があり、`until_id >= その境界`(今回の取得範囲が、既存の完全な範囲と連続している)」ときだけ延長する。
5. `write_if_current` のロックの中で、ノートのキャッシュと `extend_fetch_boundaries`(古い方へ動かすだけの `MIN`)を実行する。

手順1〜4と5の間に、同じ世代の別の書き込みが入りうる。ギャップ埋め(起動時・再接続時。`apply_gap_fill_boundaries`)は、打ち切られたときに、境界を**新しい方へ引き上げる**(完全と言える範囲を縮める、保守的な動き)。`commit_gap_fill_writes` が、同じカラムのロックの中で実行する。

起きうる流れ(再現は確認していない。コードの読解による):

1. 境界が `n100`。`fetch_backfill` が `n100` を読む(`until_id = n120`)。
2. 取得中に、打ち切られたギャップ埋めが、境界を `n350` へ引き上げる。`n350`〜`n100` の区間は、未取得。
3. `fetch_backfill` が、古い `n100` を基準に「`n120 >= n100` なので連続」と判断し、取得したページの最古の `n60` まで延長する(`MIN(n350, n60) = n60`)。
4. 境界が `n60` になり、未取得の `n350`〜`n100` が「完全」と主張される。以後のキャッシュ優先の backfill が、欠けたノートを、完全として返す。

ギャップ埋めの側は、すでに「ロックの中で、最新の境界を読んで計画する」作り(#452)。`fetch_backfill` だけが、ロックの外の古い写しを使っている。

### 2. update_column の失敗が、旧状態も新状態も中途半端にする

`update_column_core`(P3 で切り出し)は、次の順に動く。

1. 旧定義を読む。新しいソースを解決する(TQL の `user` ソースだけがネットワークを使う)。
2. `invalidate` の中で、新しい定義の保存、ストリームのクローズ、旧キャッシュの破棄を行う。
3. グループを探す(`load_groups`)。アカウントのホストとトークンを取る(`host_token`)。
4. `open_stream_and_fetch` で、初回取得とストリームのオープンを行う。

手順3は、読むだけで、`invalidate` の結果に依存しない(グループとアカウントは、更新で変わらない)。それなのに、`invalidate` の後にあるので、失敗すると(未知のグループ、未登録のアカウント)、新定義が保存され、ストリームが閉じ、キャッシュも消えた後に `Err` を返す。フロントは、`Err` のとき、タブを更新しないので、画面は旧定義と旧ノートのまま、バックエンドは新定義で、ストリームは閉じる。再起動するまで、画面は止まる(再編集でも直る)。

## スコープ

- 対象: 上の2点。
- 対象外:
  - **`invalidate` の後の失敗の巻き戻し**(下記「既知の制限」)。
  - キャッシュ提供の判断(取得前の読み取り)の競合。境界が、取得中に引き上げられても、判断に使った古い境界で返した範囲は、読み取りだけで、害は一時的(次の backfill から、新しい境界が使われる)。
  - 定期同期(#456 の P4)。
  - DB スキーマ、Tauri コマンドの署名、TS バインディング、フロントエンド。

## 設計

### 1. 延長計画を、ロックの中で、最新の境界から作る

`commit_backfill_writes` の引数 `extend: &[(u32, String)]` を、`extend_until: Option<&str>` に替える。`Some` は、キャッシュ対象のカラムで、値はこのリクエストの `until_id`。

`write_if_current` のクロージャの中で、`cache_fetched` の後に、次を行う。

1. `boundaries_ok`(境界の世代が現行)かつ `extend_until` が `Some(until_id)` のときだけ進む。
2. `cache.get_fetch_boundaries(column_id)` で、その時点の境界を `HashMap` に読む。読めなければ、延長を飛ばす(保守的。現状の「失敗は握りつぶす」と同じ向き)。
3. `plan_boundary_extend(&prev, until_id, &fetch.source_outcomes)` で、延長計画を作る。
4. 空でなければ、`cache.extend_fetch_boundaries(column_id, &plan)`(失敗は握りつぶす)。

`fetch_backfill` は、取得後の `extend` の計算をやめ、`cache_eligible.then_some(until_id.as_str())` を渡す。取得前に読む `boundaries` は、キャッシュ提供の判断(`effective_boundary` など)にだけ使い続ける。

#### 安全な理由

- 同じカラムへの書き込みは、すべて `write_if_current` のカラムのロックの中で実行される(`commit_*` ヘルパー)。ロックの中で読んだ境界は、他の書き込みと交錯しない。ギャップ埋めが引き上げた後に読めば、`until_id < 引き上げた境界` なので、`plan_boundary_extend` が延長を計画しない(上の流れの手順3が起きない)。
- `set_mute`(`invalidate_boundaries`)は、境界の書きロックの中で境界を捨てる。`write_if_current` は境界の読みロックを持つので、`set_mute` と排他。ロックの中で読む境界は、捨てた後なら空で、延長は計画されない。`boundaries_ok` のガード(#452)は、念のため残す(読みロックの外で控えた世代の確認として、多重の防御)。
- 行が無いソースは、`plan_boundary_extend` が延長しない(既存の境界を前提とする)ので、境界の復活は起きない。

### 2. update_column_core の順序

`load_groups` によるグループの検索と、`host_token` を、`invalidate` の**前**(`resolve_sources` の後)へ動かす。どちらも、読むだけで、`invalidate` の結果にも依存しない。失敗しても、定義、ストリーム、キャッシュ、世代のどれも変わらず、`Err` を返すだけ。

### 既知の制限

次の失敗は、`invalidate` の後で起きるので、現状のまま(新定義が保存され、ストリームが閉じ、画面は旧定義のまま。再編集で直る)。

- キャッシュ DB の書き込みの失敗(`clear_column_notes`、`cache_fetched`)。
- 通知カラムの初回取得の失敗(`fetch_notifications` が `Err`)。通常のカラムは、初回取得が失敗しても、そのソースが `Failed` 扱いになり、ストリームは開く。
- 世代が古い場合(別の `update_column` / `close_column` が引き継いだ)。これは仕様どおり(引き継いだ側が、ストリームを管理する)。

直さない理由:

- **通知の取得失敗を許容する**(空のまま開く)と、通知にはキャッシュが無く、再接続時のギャップ埋めが `last_seen_id` を起点にするので、起点なしで開いた通知カラムは、再接続しても補完されず、最初のライブ通知が届くまで空のままになる。「通知が無い」のか「取得できていない」のか区別もつかない。直すには、再接続時のギャップ埋めを起点なしでも動かす変更が要り、`stream/connection.rs` に及ぶ。
- **巻き戻す**(旧定義の保存、旧ストリームのオープン)は、通知カラムでは、旧ストリームを `last_seen_id` なしで開き直すことになり、同じ制限が残る。実装も重い。
- 実際の頻度は低い(DB の失敗と、オフライン時の通知カラムの編集に限られる)。

## 検討した代替案

- **取得前に境界を読み直す**: 取得(ネットワーク)の後で、ロックを取る前に読み直しても、ロックの外なので、同じ競合が残る。
- **`extend_fetch_boundaries` 自体を、バックエンドで、条件つきの更新にする**: 3つのバックエンド(SQLite / PostgreSQL / MySQL)のスキーマ・SQL の変更と、実 DB のテストが要る。ロックの中で読む方が、変更が小さい。
- **update_column の失敗時に、`invalidate` の後で、新定義のストリームを開く**: ストリームは生きるが、フロントは `Err` のときタブを更新しないので、画面は旧定義のまま、バックエンドとストリームだけが新定義になり、ずれが広がる。

## テスト

すべて、実装を外す(古い順序・古い計画に戻す)と落ちることを、変異確認する。

- `commit_backfill_writes`(単体。既存のテストは、新しい引数に合わせて直す):
  - 取得中に境界が引き上げられた場合(`n100` → `n350`)、`until_id = n120`、取得した最古が `n60` でも、境界は `n350` のまま。古い実装(取得前の写しで計画)なら、`n60` に延長して落ちる。
  - 連続している場合(境界 `n100`、`until_id = n120`)は、延長される(対照)。
  - `boundaries_ok` が偽(`set_mute` が捨てた後)なら、延長しない(既存の #452 のテストの移植)。
  - 行が無いソースは、延長しない(挿入しない)。
- `fetch_backfill` の配線(`mock_app()` + `State`、`wiremock`): 連続したページを取得すると、境界が延長される。
- `update_column_core`: 未知のグループ、未登録のアカウントで、`Err` を返し、定義、境界、世代(実行前に控えた `Epoch` が、まだ現行)、ストリームが変わらない。順序を元に戻す変異で落ちる。

## 影響範囲

- 変更するファイル: `src-tauri/src/commands/column.rs`(`commit_backfill_writes`、`fetch_backfill`、`update_column_core`、テスト)。
- DB スキーマ、Tauri コマンドの署名、TS バインディング、フロントエンドは変わらない。本番の挙動は、競合が起きうる場合と、`update_column` の失敗の場合にだけ変わる。
