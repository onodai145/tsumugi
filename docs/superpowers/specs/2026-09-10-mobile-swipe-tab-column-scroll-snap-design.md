# モバイル版: 左右スワイプでタブ/カラムを移動する (Issue #296) — CSS Scroll Snap版

## 背景・この版に至った経緯

最初の実装(`docs/superpowers/specs/2026-09-10-mobile-swipe-tab-column-design.md`)は、`pointerdown`/
`pointermove`をJSで監視し、横方向ジェスチャーと判定したら`preventDefault()`でネイティブの挙動を
止める「pointer-drag方式」だった。PR #328としてマージ前レビューを経た後、Android実機
(Pixel 8 Pro、Chrome DevToolsのリモートデバッグでpointerイベントを直接トレース)で検証したところ、
機能しないことが判明した。

**判明した根本原因:** `touch-action: pan-y`(縦スクロールは許可)を設定した要素上で、指の動きに
わずかでも縦方向成分が含まれると、ブラウザは早期に「これは許可された縦パンだ」と判定してタッチを
ネイティブスクロールに引き渡し、`pointercancel`を発行してJS側の処理を強制終了してしまう。人間の指で
完全に水平なドラッグをするのはほぼ不可能なため、事実上あらゆる横スワイプがこの扱いを受ける。
`touch-action`の値(pan-y/none)、`setPointerCapture`の有無、`preventDefault()`を呼ぶタイミング、
DOM変更の有無、いずれを変えても`pointercancel`の発生は変わらなかった(縦スクロールでも同様に
`pointercancel`が発生することを確認し、これがブラウザの標準的な「ネイティブスクロールへの引き渡し」の
合図であって異常ではないと判明した)。詳細は
`[[touch-action-pan-y-pointercancel-native-scroll-conflict]]`(メモリ)を参照。

この問題を回避するため、本版では横方向も本物のネイティブスクロールとして扱う**CSS Scroll Snap**方式に
全面的に置き換える。旧版で追加した`frontend/src/lib/swipeGesture.ts`(軸判定/確定判定/ラバーバンド)は
完全に不要になり削除する。`frontend/src/lib/swipeNav.ts`の`resolveSwipeTarget`ベースの「次/前を解決する」
ロジックと`AppStore.applySwipe`も、ネイティブスクロール位置による判定に置き換わるため削除する。

## スコープ

- 対象は`useMobileUi()`が`true`の場合のみ。デスクトップUIの挙動は変更しない。
- タブ送り・カラム移動の両方をCSS Scroll Snapで実現する(旧版のスコープ決定を踏襲: 「カラムの並び」は
  最上位rowの直下の子のうちtype: "leaf"のもののみが対象。ネストしたsplit配下のカラムは対象外)。

## 挙動

1. カラム内でタブが2つ以上ある場合、ノート一覧を横にスワイプするとタブが切り替わる(ネイティブスクロール
   +スナップ)。
2. 現在のタブがそのカラムの先頭/末尾タブで、さらに同方向へスワイプを続けると、指を離さず連続した
   動きのまま次/前のカラムへ移動する(スクロールチェイニングによる自然な継続)。
3. タブが1つしかないカラムでは、スワイプは直接カラム移動として働く。
4. 移動先が存在しない端(先頭カラムの先頭タブでさらに前へ、末尾カラムの末尾タブでさらに次へ)では、
   ブラウザ標準のオーバースクロール(バウンス/glow)挙動に任せる。

## タブ用スロット構成(カラム内の横スクロール+スナップ)

- 各カラムの`{#if activeTab}`ブロックを、「前タブ(あれば)/アクティブタブ/次タブ(あれば)」の
  最大3スロットを横並びに描画する内側の横スクロールコンテナに置き換える。
  - コンテナ: `overflow-x: auto; scroll-snap-type: x mandatory;`(モバイルのときのみ)。
  - 各スロット: `flex: 0 0 100%; scroll-snap-align: start;`、中身は現行の`{#snippet tabBody}`を
    そのまま使う(縦スクロールは各スロット内の既存`overflow-y-auto`のまま)。
  - タブが1つしかない/先頭・末尾タブでは、存在しない側のスロットを描画しない(2スロットまたは
    1スロットになる)。これにより、その方向のスクロール可能範囲がそこで尽き、スクロールチェイニングで
    外側のカラム移動に自然に繋がる。
- アクティブタブが変わるたび(タップでもスワイプ確定でも)、スロット構成を再計算し、`scrollLeft`を
  **アニメーションなしで**アクティブスロットの位置(3スロット中央、または端の場合は該当位置)に
  即座にリセットする。タブバーをタップして非隣接タブへジャンプした場合も同様に、アニメーションなしで
  瞬時に切り替える(既存のタップ挙動を踏襲)。

## 確定検知

`scrollend`イベント(`'onscrollend' in window`で機能検出し、非対応環境では`scroll`イベントの
デバウンス実装にフォールバック)で、スクロールが止まった時点の`scrollLeft`から実際にどのスロットに
着地したかを算出する。着地したスロットが現在の`activeTabId`と異なれば、`app.setActiveTab(group.id,
newTabId)`(既存メソッド、変更不要)を呼ぶ。

## カラム間移動

- `App.svelte`の外側`[data-columns-scroll]`コンテナ(`overflow-x-auto`)に、モバイルのときのみ
  `scroll-snap-type: x mandatory`を追加する。
- 各カラムの`<section class="column-root">`に、モバイルのときのみ`scroll-snap-align: start`を追加する。
- こちらも同様に`scrollend`(または`scroll`デバウンス)で着地カラムを検知し、`app.focusedGroupId`を
  更新する。

## パフォーマンス

- 非アクティブ(隣接プレビュー用)スロットは、`tab.notes`の全件ではなく先頭の一定件数(50件)だけ
  描画する。実際にそのスロットがアクティブになった時点でフルの一覧に切り替える。
- 全てのタブ(表示中かどうかに関わらず)はストリーミングで継続的にノートを保持しているため
  (`domain`層の設計上、非表示タブもWebSocket購読は維持される)、隣接タブをプレビュー表示しても
  追加のネットワーク取得は発生しない。

## 状態遷移

- `activeTabId`/`focusedGroupId`の更新は、`scrollend`(またはデバウンスされた`scroll`)で着地が
  確定した時点、またはタブバーのタップ時にのみ行う。スクロール中の中間状態では更新しない。
- Backstage/モーダル/リアクションピッカーなど他のオーバーレイが開いている間のジェスチャー無効化は
  不要になる(ネイティブスクロールなので、オーバーレイが`fixed`/portalで正しく最前面に描画されている
  限り、下のスクロールコンテナへのタッチは自然にブロックされる)。

## 非スコープ・撤去する実装

- `frontend/src/lib/swipeGesture.ts`とそのテスト: 削除(pointer-drag方式専用のロジックのため不要)。
- `frontend/src/lib/swipeNav.ts`の`resolveSwipeTarget`/`topLevelLeafGroupIds`とそのテスト: 削除
  (ネイティブスクロール位置による判定に置き換わるため)。
- `AppStore.applySwipe`とそのテスト: 削除(`setActiveTab`/`focusedGroupId`直接更新で足りるため)。
- `Column.svelte`のpointerイベントハンドラ(`onSwipeDown`/`onSwipeMove`/`onSwipeUp`/`onSwipeCancel`)、
  `settle()`、ドラッグ用`$state`、`touch-action`スタイル: 全て削除しScroll Snap方式に置き換える。
- ネストした分割(split)配下のカラム間でのスワイプ移動(旧版から継続して非スコープ)。
- デスクトップUIでのスワイプ対応(旧版から継続して非スコープ)。

## テスト方針

- スロット構成の算出(前/アクティブ/次のどれを描画するか、非表示スロットのノート件数制限)は
  純粋関数として切り出し、Vitestでユニットテストする。
- `scrollend`検知からの着地スロット算出ロジックも、`scrollLeft`とコンテナ幅から算出する純粋関数として
  切り出し、ユニットテストする。
- 実際のネイティブスクロール・スナップ挙動そのものはjsdomでは検証できないため、既存e2e(デスクトップ
  想定のtauri-driver構成)への追加は行わず、Android実機での動作確認を最終確認とする。**今回は
  実機確認を計画の完了条件に含める**(前版はここを省略して問題を見逃した)。
