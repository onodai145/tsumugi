# MML の音色パラメーター(エンベロープ・ビブラート・デチューン)の設計

Issue #499 の残りの候補のうち、「音色のパラメータ」。ポルタメントは、仕組みが違うので、別の PR にする(下の「範囲」)。関連: `2026-10-16-issue-494-mml-timbre-design.md`(音色 `@`)、`2026-10-30-issue-499-mml-drumkit-design.md`(`@drumkit`)、`2026-10-20-issue-499-mml-macro-design.md`(`$` マクロ)。

## 目的

音色(`@`)は、音の作り(エンベロープ・ビブラートなど)が音色ごとに固定で、MML から変えられない。音の立ち上がり・減衰・余韻の長さ、ビブラートの有無、音程のずらしを、MML の中で、トラックごとに指定できるようにする。

成功条件:

- `y10,200,60,300 c d e` のように、トラックの状態としてパラメーターを書け、誤りは今までどおり「N 文字目」の位置つきエラーで返る。
- 今まで通っていた MML は、同じ音になる(`y` `m` `k` は今は構文エラーなので、保存済みの MML の意味は変わらない)。
- 打楽器(`drum` `noise` `drumkit`)の音は変わらない。

## 範囲

含める:

- 3 つのコマンド: エンベロープ `y`、ビブラート `m`、デチューン `k`(文字は下の表)。
- それに伴う、Rust(パーサー、`NoteEvent`)、フロント(音源、字句解析、入力補助キー、「記法」ヘルプ)、ユーザーガイドの追随。

含めない:

- ポルタメント(別の PR。前の音の高さを覚えて滑らせる必要があり、和音・複数音の同時発音との組み合わせを決める必要がある)。
- ビブラートの遅れ(Tone.js の `Vibrato` に遅れの部品がない)。
- パラメーターを音ごとに変える書き方、ピッチベンド、エフェクト(別の項目)。
- 打楽器(`drum` `noise` `drumkit`)への効果。

## 原典の確認結果(2026-10-30)

sakuramml-rust(README と `docs/syntax-note.md` `syntax-command-list.md` `syntax-voice.md`)と、ffmml(`sile/ffmml` の README・`src/commands.rs`・`src/macros.rs`・`src/types.rs`)、MCK の資料(`mckc-e.txt`、`mck_guide_v1.0.txt`)で確認した。

| 項目 | sakuramml | ffmml / MCK |
|---|---|---|
| ビブラート | `VibratoRate(n)` `VibratoDepth(n)` `VibratoDelay(n)`(0〜127、NRPN で音源に依存) | `@MP0={遅れ 速さ 深さ}` で定義し、`MP0` で選び、`MPOF` で止める。トラックの状態で、次の音から効く。 |
| ポルタメント | `Slur(SLUR_PORT, 長さ)` と `&` | なし(MCK の資料に「ポルタメントのコマンドはなさそう」とある)。近いものはピッチエンベロープ `EP`。 |
| デチューン | `FineTune(n)`(0〜127、64 が中央、±100 セント。RPN で音源に依存) | `D数値`(−127〜126、`D255` で解除) |
| エンベロープ | `EGAttack` `EGDecay` `EGRelease`(NRPN。サステインはない) | ADSR はない。`@v0={15 14 13 …}` のフレームごとの音量の並び。 |

分かったこと:

- 4 項目を同じ書き方で持つ方言はない。標準はないので、tsumugi の記法は自分で決める。
- いずれもトラックの状態として、次の音から効く(MCK の `MP` は明記、sakuramml は不明)。tsumugi の `t` `v` `q` と同じ扱いにする。
- #499 の本文と、マクロの spec(`2026-10-20-issue-499-mml-macro-design.md`)にある「ffmml の `@@`」は、MCK の「エンベロープのマクロ」の一種を指していた。正確には、`@@n` は**音色(デューティー)のマクロ**の選択で、音量のエンベロープは `@v`、ビブラートは `MP` で選ぶ。マクロの spec の結論(フレーズの再利用ではない)は変わらない。

## 決定

| 項目 | 決定 | 理由 |
|---|---|---|
| 記法 | 1 文字コマンド `y` `m` `k`。数字はカンマで並べる | `t` `v` `q` と同じ試し方。マクロ `$` と相性がよい。今は構文エラーの文字なので、既存の MML に影響しない。 |
| 状態 | トラックの状態。書いたところから後の音に効く。ループ・マクロ・連符の中でも書ける。和音の中には書けない(和音の前に書く) | `t` `v` `q` と同じ。 |
| 解除 | `y0` `m0` `k0`(`0` 1 つ)で、音色の既定に戻す | 「何も指定しない」と同じ状態に戻せる。 |
| 打楽器 | `drum` `noise` `drumkit` は無視する | 高さの持続がなく、効果が意味を持たない。 |
| NoteEvent | 音ごとに `params` を持たせる(すべて既定なら `null`) | 描画側が、音ごとにどのパラメーターか分かる必要がある。 |
| デチューンの実現 | 音源に渡さず、描画側が、鳴らす周波数に `2^(セント/1200)` を掛ける | 音源の組に数えない。実測で、デチューンを 201 通りにすると、音源を分ける方式は描画に 169 秒かかった(「実装後の確認」)。聞こえ方は同じ(周波数が同じ割合でずれる)。 |

## 記法と意味

| コマンド | 書き方 | 意味・範囲 |
|---|---|---|
| エンベロープ | `y a,d,s,r` | アタック(ミリ秒、0〜2000)、ディケイ(ミリ秒、0〜2000)、サステイン(0〜100 %)、リリース(ミリ秒、0〜600)。4 つすべて必要。解除は `y0`。 |
| ビブラート | `m 速さ,深さ` | 速さ(Hz、1〜20 の整数)、深さ(1〜100。音程の揺れの片側の幅で、おおよそのセント。速さが遅いと頭打ちになり、1 Hz は約 ±27 セント、4 Hz 以上は 100 まで)。解除は `m0`。`lead` が持つ組み込みのビブラートは、`m` と関係なく残る(`m` はその上に足される)。 |
| デチューン | `k セント` | 音程のずれ(セント、−100〜100。`k+12` `k-12` と書ける)。解除は `k0`。 |

- リリースの上限(0.6 秒)は、`TAIL_SEC`(最後の音の余韻が切れないための余白)と同じ。
- `y` は、エンベロープの `modulationEnvelope`(FM・AM 音色の倍音の変化)は変えない。音量のエンベロープ(`envelope`)だけを置き換える。
- `y` を書いても、音色を切り替えたとき(`@`)は、パラメーターは保たれる(音色ごとの既定値とは別に、トラックが持つ)。
- 音の途中(タイ `&` で延びた音)の、パラメーターは、先頭の音のものを使う。和音の音は、和音を閉じた時点の状態を使う。
- 範囲外・形の誤りは、今までどおり位置つきのエラーにする。`y` の `0`(解除)だけが 1 つの数字で許される。例: `y10,200,60`(足りない)、`y2001,0,0,0`(範囲外)、`m21,1`、`k101`。

## エラー

| 入力 | 位置 | メッセージ(案) |
|---|---|---|
| `y` の後に数字がない | `y` | `y` の後に数値が必要です |
| `y` の数が 4 つでない(`0` 1 つは解除) | その区切りの位置 | `y` は `y0`(解除)か `y a,d,s,r`(4 つの数)です |
| 範囲外 | 数字の先頭 | アタックは 0〜2000 ミリ秒です、など |
| 和音の中の `y` `m` `k` | その文字 | 和音の中には書けません(和音の前に書いてください) |

## 他の命令との関係

- **`@drum` と `@drumkit`**: `@drum` の後に `k` と数字が続く MML(`@drumk0 c`)は、`@drum` + デチューン `k0` になる。今まで構文エラーだった入力が通るようになるだけで、既存の MML の意味は変わらない。`@drumkit` は、最長一致で、今までどおり `drumkit` になる(`kit` の `i` は数字でも符号でもないため、`k` のデチューンとは読めない)。
- **マクロ `$`**: 本体にも書ける(文字の置き換えなので)。
- **タイ・ゲート `q`**: 音の長さを変えるだけで、パラメーターとは独立。

## Rust の変更

- `domain/mml.rs`: `NoteEvent` に `params: Option<TimbreParams>` を足す。`TimbreParams { envelope: Option<EnvelopeParams>, vibrato: Option<VibratoParams>, detune: i16 }`、`EnvelopeParams { attack_ms: u32, decay_ms: u32, sustain: u8, release_ms: u32 }`、`VibratoParams { rate_hz: u8, depth: u8 }`。すべて既定なら `None`。`tauri.gen.ts` は再生成される(`params` が `TimbreParams | null` で増える)。
- `mml.rs`: `Op::Envelope` `Op::Vibrato` `Op::Detune`、`TrackState` の状態、パース(`y` `m` `k`)、和音の中のエラー、音符の生成時に `params` を載せる。
- パーサー側の影響: `Timbre` の「最長一致」のテストの注記(`kit` は命令の先頭にならない)を更新する。

## フロントの変更

- 描画: パラメーターの組(エンベロープ・ビブラート)ごとに、別の音源を作る。`PolySynth` は、描画中に設定を時刻つきで変えられないため。音源は、(トラック, 音色, エンベロープ・ビブラートの組)で使い回す。エンベロープは `synth.set({ envelope })`(`DuoSynth` は `voice0` と `voice1`、`MonoSynth` は `envelope`)、ビブラートは `Tone.Vibrato`(エフェクト)を音源の出力に挟む。デチューンは音源に渡さず、鳴らす周波数に `2^(セント/1200)` を掛ける(音源の組に数えない。打楽器は無視)。
- 字句解析(`mmlLexer.ts`): `y` `m` `k` を command、後ろの数字を number、カンマを separator にする。
- 入力補助キー(`mmlKeys.ts`): 「音色パラメーター」のグループ(`y` `m` `k` `,`)を足す。
- 「記法」ヘルプ、ユーザーガイド: 書き方と範囲を足す。

## テスト

- Rust: 各コマンドの読み取りと範囲(境界値、`0` の解除、`k+12` `k-12`)、エラーの位置(足りない数・範囲外・和音の中)、トラックごとの独立、ループ・マクロの中、タイと和音での状態、`NoteEvent` の `params`(すべて既定なら `None`)、`@drumk0 c`、`$` を含まない既存の MML の結果が変わらないこと。
- フロント(Vitest): 字句解析(`y10,200,60,300` `m5,30` `k-12` `y0`)、`mmlKeys`、描画のパラメーターごとの音源の使い回し(偽の Tone)、打楽器が無視すること、ヘルプ。
- 実機(手動、隔離した Xvfb): 15 種すべての描画がエラー・NaN なしであること、`y` の極端な値(アタック 2000・リリース 600・サステイン 100)で、ピークが 0.36 以下であること、ビブラートとデチューンで描画が失敗しないこと、パラメーターを付けた 2772 音の描画時間。**音が実際に鳴ること(聞こえ方の良し悪し)は、音声デバイスがないので確認できない。**

## 未確認・リスク

- `Tone.Vibrato` の深さ(0〜1 の遅れの揺れ)は、音程の揺れの大きさ(セント)とは、単純に対応しない。最終レビューの指摘を受けて、実際の描画で測った(`@5 sine`、深さ 0.1 で、1 / 5 / 20 Hz がそれぞれ ±2.7 / ±13.6 / ±53.8 セント。つまり、揺れ ≈ 27 セント × 速さ × 深さ)。`m` の深さを、速さに依らない、片側の揺れの幅(セント)にするため、Tone に渡す値を `深さ / (27 × 速さ)`(上限 1)にした。
- エンベロープを極端にすると、音量(RMS)が大きく変わる。ピークの上限(0.36)は実測で確かめるが、各音色の聞こえる大きさの揃え方は、聴いて決める。
- パラメーターの組が多い MML(音ごとに値を変える)では、音源が増えて描画が遅くなる。組の数に上限は設けない。2772 音で、全部違う組(最悪)の描画時間を測り、遅すぎるなら上限を設ける。
- `y` `m` `k` の文字は、将来の命令(ポルタメントなど)との兼ね合いで、変えたくなるかもしれない。今は構文エラーなので、決めるのは今回。

## 実装後の確認

2026-10-30、ブランチ `feat/issue-499-mml-timbre-params`。隔離インスタンスは、`Xvfb :95`(1280x900)、`dbus-run-session`、`XDG_*` を `/tmp` 直下の短いパスに置き、`WAYLAND_DISPLAY` を unset、`GDK_BACKEND=x11` で、`frontend/dist` を作り直してから `cargo build` した `target/debug/tsumugi` を直接起動した。ダミーのアカウント(`misskey.invalid`)だけを `settings.json` に書いた。起動した全プロセスに一意なトークンを環境変数で付け、確認のあと、トークンで特定した PID だけを止めた(Xvfb のロックファイルと隔離ホームも削除済み)。ユーザー自身の `cargo tauri dev` には触れていない。

仕様からの変更:
- デチューンの実現: 最初の実装(`PolySynth.set({ detune })` で音源の組ごとに分ける)は、デチューンを 201 通りにした 2814 音(`@0 t240 l64 [k-100 c … k100 c]14`、再生 44 秒)の描画に 169 秒かかった(パラメーターなしの同じ長さは 29 秒。音源の組が 1 つ増えるごとに、約 0.7 秒増える)。ユーザーと相談して、デチューンは音源に渡さず、描画側が鳴らす周波数に `2^(セント/1200)` を掛ける方式に替えた(「決定」の表を参照)。聞こえ方は同じ(波形のピーク・RMS も同じ)。替えたあとは、同じ MML の描画が 26.4 秒(パラメーターなしは 25.4 秒)になった。組の数に上限は設けていない。

確認できたこと:
- 自動テスト: `cargo test` は 802 件通過(失敗 0、`#[ignore]` 61 件)。`pnpm check` は 0 errors(既存の `UrlPreviewCard.svelte` の警告 1 件のみ)。`pnpm test` は 99 ファイル・1101 件通過。`rustfmt --check src/mml.rs` の差分は 4 件(`main` と同じ)。確認後の `git status` は、コミット前の変更だけ。
- 旋律の音色 12 種(`@0`〜`@11`、`c4`): パラメーターなしのピーク 0.1238〜0.2744(`@0` は 0.2031、RMS 0.0436。#494 の校正値と同じ)。極端なエンベロープ `y0,0,100,0`(サステイン最大)はピーク 0.1241〜0.2788、`y2000,0,100,600`(アタック最長・リリース最長)はピーク 0.0310〜0.0614。**全音色で 0.36 以下**。エラー・NaN なし。`y2000,0,100,600` でも、末尾 0.05 秒の最大値は 0.0001 以下(余韻は切れていない)。
- パラメーターが実際に効くこと(`@0 c4` を基準に、WAV の内容を比べた): `k100` `k-100` `m20,100` `m1,1` `y2000,0,100,0` は、いずれも基準と内容が違う。`y2000,0,100,0`(アタック 2 秒)は 0.5 秒の音がほとんど立ち上がらず、ピークは 0.0006。`y0` `m0` `k0` で解除すると、基準と 1 バイトも違わない(同じハッシュ)。`@10 lead` でも、`y` `m` `k` が効く。
- 打楽器: `@12 c4` と `@12 y0,0,100,0 m20,100 k100 c4`、`@14 o2 c4` と `@14 y0,0,100,0 m20,100 k100 o2 c4` は、WAV の内容が同じ(パラメーターを無視している)。
- 描画時間(2814 音前後、`@0 t240 l64`): パラメーターなし 25.4 秒、デチューン 201 通り 26.4 秒(替えたあと)。エンベロープの組を 20 通り(1980 音、再生 30.9 秒)にした場合は 17.2 秒(パラメーターなしの同じ長さは 12.2 秒。組 1 つあたり約 0.25 秒)。
- UI: 「記法」に `y10,200,60,300 エンベロープ(…)` と `y0 m0 k0 で音色の既定に戻す…` の行が出る。色分けは、`y` `m` `k-` とカンマが `mml-command`、数字が `mml-number`。モバイル UI で、入力補助キー `y` `m` `k` `,` が出て、押すとカーソル位置に入る。エラー位置は、`y10 c` が 5 文字目、`y2001,0,0,0 c` が 2 文字目、`'cy1,2,3,4'4` が 3 文字目で、「N 文字目」を押したときのカーソルがその位置に移る(印の文字を打って確かめた)。

最終レビューのあとの変更と確認:
- ビブラートの深さ: レビューが、`Tone.Vibrato` の揺れが速さに比例し、範囲の両端が使いにくいと指摘した。`@5 sine`(C4 の 4 秒の音、ゼロ交差から 1 周期ごとの周波数を出して、2〜98 % の幅を見た)で測ったら、変更前は深さ 10 で、1 / 5 / 20 Hz がそれぞれ片側 ±2.7 / ±13.6 / ±53.8 セントで、指摘のとおり「約 27 セント × 速さ × 深さ」だった。Tone に渡す値を `深さ / (27 × 速さ)`(上限 1)に変えたあと、片側の揺れの幅(2〜98 % の半幅)は、`m1,10` が 10.0、`m5,10` が 10.0、`m20,10` が 9.9、`m5,30` が 30.1、`m20,40` が 39.8、`m5,100` が 100.5、`m20,100` が 99.7(セント)になり、速さに依らず、深さ(セント)に一致した。`m1,100` は 27.1 セントで頭打ち(1 Hz の上限)。パラメーターなしは ±0.1 セント。

確認できなかったこと:
- 実際に音が鳴ること、聞こえ方(エンベロープ・ビブラート・デチューンの効き具合、音量バランス)の良し悪し。音声デバイスが無いので、波形の数値までを確認した。聴いた人の評価で、後から直す前提。
- エンベロープ・ビブラートの組が極端に多い MML(数百通り)の描画時間。20 通りまでを測った。
- Android の実機・エミュレーター、macOS / Windows。
