# カラム読み上げ 段階2: デスクトップ向けの内蔵 VOICEVOX CORE (Issue #625)

段階1(PR #662、`docs/superpowers/specs/2026-11-19-issue-625-column-speech-design.md`)で、`SpeechEngine` trait と外部の VOICEVOX 互換エンジンへの接続、読み上げ機能一式を入れた。この spec は段階2として、**デスクトップ(Linux・macOS・Windows)で、外部エンジンを立てなくても読み上げられる内蔵エンジン**を足す。Android の内蔵は段階3(別 spec)。

## 決定事項(合意済み)

- 声の範囲は**公式の VVM のうち、読み上げ用のスタイルを持つ 27 個**(`voicevox_vvm` 0.17.1 の `0`〜`25` と `n0`。1 個あたり約 55〜75 MB、合計約 1.65 GB。`s0` は歌声用のスタイルだけなので含めない)。使う分だけを個別に取得する。
- 組み込み方は**公式の C API を、実行時に取得して動的ロード**する(`libloading`)。Rust クレート `voicevox_core` の git 依存は採らない(理由は下記)。
- 声(VVM)の取得・削除は、**設定画面に管理画面を別に置く**(翻訳モデルの管理画面と同じ作り)。声の選択肢には取得済みの声だけを出す。
- 同意は、最初の取得の前に 1 回。規約が変わったら再同意。クレジット(`VOICEVOX:キャラ名`)は声の選択の横に出す。
- 既定のエンジンは `external` のまま。既存の利用者の挙動は変わらない。

### 組み込み方の比較(案 A を採用)

| 案 | 長所 | 短所 |
|---|---|---|
| **A. C API を実行時取得・動的ロード** | アプリのビルドに C++ や git 依存が増えない。CI・インストーラーが重くならない。CORE の更新は固定値の差し替えだけ | C API の FFI ラッパを自前で書く(`unsafe`)。CORE 本体も実行時取得になる |
| B. Rust クレートを git 依存でビルド | 型付きの安全な API | `ort` と `open_jtalk`(C++)の git 依存が入り、ビルドが重くなる。`publish = false` で更新を追う手間が続く。MSRV 1.89 への引き上げが要る |

`local-translate` の llama.cpp で、C++ ビルドが CI・Windows のパス長・macOS の最小バージョンなどの問題を何度も生んだので、同じ負担を増やさない。取得物を SHA-256 で検証してロードする流れは、翻訳モデルの `translate/download.rs` と同じ形に揃えられる。

## 目標 / 非目標

目標:

- 設定で「内蔵 VOICEVOX CORE」を選び、エンジン一式と声(VVM)を取得すると、外部エンジンなしで読み上げられる。
- 外部エンジンは引き続き選べる。外部と内蔵を切り替えても、カラムの声の設定(`voice_id`)がそのまま使える。
- 読み上げの失敗(取得漏れ・ロード失敗)が、ノートの受信・表示・通知を妨げない。
- 内蔵に対応しない環境では、内蔵が選べず理由が分かる。

非目標(段階2):

- Android の内蔵(段階3)、Windows arm64、BSD。
- GPU(DirectML・CUDA)、ユーザー辞書、ストリーミング合成、歌声、抑揚・ピッチの調整。
- AivisSpeech の内蔵、取得元のミラー、CORE・VVM の自動更新(版の更新はアプリの更新に載せる)。
- 段階1の機能(キュー・ワーカー・再生レーン・フロントの発火判定)の変更。

## 設計

### 1. 範囲と取得物

**対応する環境**: Linux(x64・arm64)、macOS(x64・arm64)、Windows(x64)。それ以外では、設定に「この環境では使えません」と出し、内蔵を選べない。ネイティブの呼び出し(`ffi.rs` の `NativeCore`)だけ `cfg(desktop)` で囲む。ほかのモジュールとコマンド・イベントは全環境でビルドする(TS バインディングを環境で変えないため)。Android・Windows arm64・BSD では `supported = false` を返す。実行時に、OS と CPU の組から取得物を引き、組が無ければ `unsupported` にする。

**取得物**(`catalog.rs` の固定値。URL・SHA-256・サイズ・版を持つ。SHA-256 は実装の最初のスパイクで実物から計算して入れる)。

| 種類 | 取得元 | サイズ | 取得のタイミング |
|---|---|---|---|
| CORE(C API) | `VOICEVOX/voicevox_core` 0.17.1 の `voicevox_core-<os>-<arch>-0.17.1.zip`(`<os>-<arch>` は `linux-x64` / `linux-arm64` / `osx-x64` / `osx-arm64` / `windows-x64`) | 約 1.2〜1.5 MB | エンジン一式 |
| ONNX Runtime | `VOICEVOX/onnxruntime-builder` の `voicevox_onnxruntime-<platform>-1.17.3.tgz`(`<platform>` は `linux-x64` / `linux-arm64` / `osx-x86_64` / `osx-arm64` / `win-x64`) | 約 4.7〜6.8 MB | エンジン一式 |
| 辞書 | `r9y9/open_jtalk` v1.11.1 の `open_jtalk_dic_utf_8-1.11.tar.gz`(公式ダウンローダーと同じ取得元) | 約 23.6 MB | エンジン一式 |
| 声 | `VOICEVOX/voicevox_vvm` 0.17.1 の `<N>.vvm`(`0`〜`25`、`n0`) | 約 55〜75 MB | 管理画面から個別に |

- ONNX Runtime は 1.17.3 にする。CORE 0.17.1 は 1.17.3 以上 1.24 未満に対応するが、1.23.2 は prerelease なので、正式版の最新の 1.17.3 を選ぶ。CORE 0.17.1 の推奨は 1.23.2(prerelease)だが、パスを明示すれば 1.17.3 で動くことを Linux で確かめた(スパイクノート)。
- 「エンジン一式」(CORE・ONNX Runtime・辞書、約 30〜32 MB)は 1 回で取得する。声(VVM)は使う分だけ取得する。
- カタログは、VVM ごとに、含まれるキャラクター名・スタイル(ID と名前)を持つ。声の一覧は、VVM をロードせずにカタログから作れる。スタイル ID は VOICEVOX ENGINE と同じなので、外部エンジンと内蔵で `voice_id` が共通になる。
- CORE・ONNX Runtime・辞書・VVM の版は、アプリの更新でカタログを差し替える形でのみ変える。

**規約と同意**:

- 規約は 2 つ。「VOICEVOX 音声モデル利用規約」(`voicevox_vvm` の `TERMS.txt`)と「VOICEVOX ONNX Runtime 利用規約」(tgz 内の `TERMS.txt`。リリース本文と同じ内容)。取得の前に読めるよう、**アプリに規約の写しを埋め込み**、確認画面で見せる。
- 同意版は、改行コードを除いた 2 つの規約の写しの SHA-256。`SettingsData.speech_core_terms_version` に保存する。翻訳の `local_model_license_version` と同じ扱いで、**設定のエクスポートに含めず、インポートでは現在の値を維持する**。
- **同意は Rust 側で強制する**。取得を始めるコマンドの引数の同意版が、埋め込みの版と一致しなければ拒否する。同意版は、取得の開始に成功したあとに保存する。
- 規約の写しが上流と食い違っていないかは、`#[ignore]` のテストで確かめる(上流の取得が要る)。
- クレジット(`VOICEVOX:キャラ名`)は、声の選択の横と、ユーザーガイドに載せる。表記は規約の `## キャラ名` の節から取り出す。`n0` は「VOICEVOX Nemo」。規約に個別の節がない `雨晴はう` は「VOICEVOX:雨晴はう」(全体の規約に従う)。

### 2. Rust の構成

`WorkerContext::engine()` が、エンジンを選ぶ唯一の接点。段階1のキュー・ワーカー・再生・フロントの発火判定は変えない。

新しい部品(`src-tauri/src/tts/voicevox/`。ネイティブの呼び出しだけ `desktop`):

| ファイル | 役割 |
|---|---|
| `catalog.rs` | 固定値(取得物・VVM 27 個・各 VVM のキャラ/スタイル・規約の版) |
| `store.rs` | `app_data_dir/voicevox/` の配置(版ごとのディレクトリ)と、ディスク上の状態の検査 |
| `archive.rs` | zip(C API)と tgz(ONNX Runtime・辞書)の展開。必要なファイルだけを取り出す。パスの脱出(zip-slip)・展開後のサイズ上限・シンボリックリンクを拒否する |
| `ffi.rs` | `libloading` で C API を呼ぶ薄いラッパ(約 15 関数)。**`unsafe` はこのファイルに閉じ込める**。C 側が返す文字列・WAV の解放もここで行う。背後に `CoreBackend` trait を置き、テストでは偽の実装に差し替える |
| `engine.rs` | `CoreEngine: SpeechEngine` |
| `packs.rs` | 取得・削除・進捗の状態機械(翻訳の `LocalModels` に相当)。同時に走る取得は 1 つ。進捗は `Notify` で約 250ms に間引く。Tauri には依存せず、イベントへの変換は `commands/` 側 |

- **再利用**: `translate/download.rs` の `download()`(Range 再開・SHA-256 検証・キャンセル・30 秒の停止検出)を、そのまま使う。`ModelSpec` は URL・サイズ・ハッシュだけを持つ汎用の形。`model_store.rs` の空き容量の判定も使う。
- **接続**: `SpeechEngineKind` に `VoicevoxCore` を足し、`AppContext::engine()` が設定に応じて `ExternalEngine` か `CoreEngine` を返す。
- **ロード**: ONNX Runtime・辞書・`Synthesizer` は最初の合成で一度だけ作る。VVM は声が必要になったときに、そのぶんだけロードする。10 分使われなければアンロードする(翻訳モデルと同じ。`Synthesizer` と VVM を落とす)。
- **依存の追加**: `libloading`(Android・iOS 以外のターゲットだけ)、`zip`、`tar`、`flate2`(全環境。アーカイブの展開は全環境でビルドするため)。
- **安全上の方針**: ダウンロードしたネイティブライブラリを `dlopen` するので、ロード前にファイルサイズを固定値と照合する。検証は取得時の SHA-256 に頼り、ロードのたびの再ハッシュはしない(ユーザー自身のデータディレクトリを信頼する前提)。

### 3. データフロー・エラー・スレッド

読み上げの経路は変わらない(`columnNote` → `speak_note` → キュー → ワーカー → `engine.synthesize()` → WAV → 再生レーン)。内蔵のときの `synthesize()` は次のとおり。

1. 声の ID(文字列)をスタイル ID の数値にする。カタログに無ければ `ERR_NO_VOICE`。
2. そのスタイルを含む VVM をカタログから引く。ディスクに無ければ `ERR_NOT_READY`。
3. 初回だけ ONNX Runtime・辞書・`Synthesizer` を作る。足りない VVM はロードする。
4. `audio_query` を作り、`speedScale` と `volumeScale` を設定して、`synthesis` で WAV にする。

- **スレッド**: 合成は CPU を使う同期処理なので `spawn_blocking` で動かす。ワーカーは 1 本で逐次なので、`Synthesizer` は同時に 1 回しか呼ばない。推論のスレッド数はコア数の半分(最低 1)に絞る(既定の「全コア」だと、合成中に UI が重くなるため)。合成中に `stop_all` が来ても合成は止められない。既存の `handle_item` と同じで、結果を捨てる。
- **エラー**(利用者向けの文面にパス・URL は含めない):

| 状況 | 扱い |
|---|---|
| エンジン一式が未取得、または声の VVM が無い | `ERR_NOT_READY`(段階1の失敗カウントに乗る。3 回連続で `Error` 状態) |
| ライブラリのロード失敗 | `ERR_ENGINE_LOAD`。次の合成で再試行する(失敗は覚えない) |
| 合成の失敗 | `ERR_BAD_RESPONSE` と同じ扱い |
| 取得の失敗 | 翻訳モデルと同じ `DownloadError` の文面 |

- **削除と更新**: 声(VVM)の削除は、アンロードしてからファイルを消す。ONNX Runtime は一度ロードするとプロセス終了まで外せない。Windows ではロード中の DLL を消せないので、エンジン一式の削除が失敗したときは「アプリを再起動してから削除してください」と案内する。版が変わるときは版ごとの別ディレクトリに取得し、古い版は次の起動時にロード前に掃除する。

### 4. 設定と UI

- `SpeechSettings.engine` に `voicevoxCore` を足す(`rename_all = "camelCase"`)。既定は `external`。`SettingsData` に `speech_core_terms_version` を足す(`#[serde(default)]`)。`#[serde(default)]` の追加フィールドは生成される TS で省略可能になるので、`lib/speechDefaults.ts` の `withSpeechSettingsDefaults` に追加キーを補う。
- 設定 → 読み上げ(`SpeechSection.svelte` を拡張し、内蔵用に `SpeechCoreSection.svelte` を足す):
  1. エンジンの選択(外部の VOICEVOX 互換 / 内蔵 VOICEVOX CORE)。対応しない環境では内蔵を選べず「この環境では使えません」と出す。
  2. 内蔵を選んだときの「エンジン一式」の行。状態は 未取得・取得中(進捗とキャンセル)・取得済み・失敗。「取得」を押すと規約の確認を出し、同意すると Rust 側が同意版を保存して取得を始める。
  3. 「声の管理」。VVM を 27 行で並べ、各行に 含まれるキャラ名・サイズ・状態・取得/削除 を出す。取得はエンジン一式の取得後にだけ押せる。
  4. 声の選択肢(全体の既定・カラムごと)。取得済みの声だけを出し、選んだ声の横に `VOICEVOX:キャラ名` のクレジットを表示する。
  5. 「試し聞き」は、外部と同じボタンで動く。
- カラムの `voice_id` はエクスポートに含まれる。別のマシンでその声が未取得だと読み上げは `ERR_NOT_READY` になる。このとき設定画面に「この声は未取得です」と出す。
- コマンドとイベント(`specta_builder()` に登録し、TS バインディングを再生成する): イベント `SpeechCoreStatusChanged`(エンジン一式と各 VVM の状態)、コマンドは 状態取得・取得開始(対象と同意版を引数に取る)・キャンセル・削除。声の一覧は、新しいコマンド `list_speech_core_voices`(取得済みの声だけ)で返す。外部エンジンの `list_speech_voices` は URL を引数に取るので、分岐させない。
- 新しい UI の値は `docs/design/style-guide.md` の既存の目盛りだけを使う。

## テストと検証

自動テスト:

- **カタログ**: 27 個の VVM、スタイル ID の重複なし、ハッシュとサイズの形式、対応する環境ごとの取得物の解決。上流の実物との照合(サイズ・ダイジェスト・規約の写し)は `#[ignore]` のテストに分ける。
- **`archive.rs`**: zip-slip、シンボリックリンク、展開後のサイズ上限、目的のファイル以外を取り出さないこと。
- **`packs.rs`**: 翻訳のテストと同じ作りで、`axum` の偽サーバーに対して 取得・再開・キャンセル・ハッシュ不一致。**同意版が違うと拒否される**こと。
- **`engine.rs`**: `CoreBackend` の偽の実装で、声の ID の変換、VVM の不足(`ERR_NOT_READY`)、速度と音量の反映。
- **実物**: `#[ignore]` のテストで、公式の取得物を使って実際に合成し、WAV のヘッダ・長さ・無音でないことを確かめる(`TSUMUGI_TEST_CORE_DIR`)。
- **フロント(Vitest)**: `SpeechCoreSection` の各状態と規約の確認、ストアのイベント購読、`speechDefaults` の追加キー。
- **バインディング**: `generates_frontend_bindings` で、新しいコマンドとイベントを確かめる。

この環境での確認:

- plan の最初に小さなスパイクを置く。固定した取得物の組が、Linux で実際にロードして合成できること、所要時間とメモリ、必要なシステムライブラリ(例: `libgomp`)、C API のライブラリのファイル名を測る。結果はスパイクノートに残す。
- 実際のアプリ(Xvfb)で、取得 → 合成 → 状態イベントの流れを確認する。

確認できないこと(PR に明記する):

- スピーカーからの実際の音。
- macOS・Windows での実行(CI はビルドとテストの通過まで)。
- Android のビルドが `cfg` で除外されていること(`android-build` の CI で確かめる)。

ドキュメント: ユーザーガイドの「読み上げ」に内蔵エンジンの節を足す。`CLAUDE.md` の `tts/` の記述を更新する。

## 段階分け

- 段階1(PR #662・マージ済み): エンジン抽象・外部エンジン・読み上げ機能一式。
- 段階2(この spec): デスクトップ向けの内蔵 VOICEVOX CORE。
- 段階3(別 spec・別 plan): Android の内蔵。Android 向けの CORE ビルドは arm64 と x86_64 だけで、ONNX Runtime は別途取得する。16KB ページへの対応には VOICEVOX ONNX Runtime 1.22 以降が必要。先に実機で速度・メモリ・16KB ページを実測するスパイクを行い、実用的なら進める。armv7 と i686 では内蔵を無効にする。段階2で作る `catalog.rs`・`archive.rs`・`packs.rs`・`ffi.rs` は、段階3でも使える形にしておく(取得物の組を足すだけで済むように、環境の組を引く関数を 1 か所に集める)。

## リスクと未確認事項

- **ネイティブコードのクラッシュはアプリごと落ちる**: C API 内部のクラッシュは、`catch_unwind` では捕まえられない。別プロセスに分ける案もあるが、構成が重くなるので採らない。公式の配布物を SHA-256 で固定することで許容する。
- **規約の更新**: 上流の規約が変わると、埋め込みの写しが古くなる。`#[ignore]` の照合テストで検知し、版を更新したときは再同意になる。
- **サードパーティの取得元**: 辞書は `r9y9/open_jtalk` の GitHub リリースから取得する(公式ダウンローダーと同じ)。取得元が消えると新規の取得が失敗する。取得済みの利用者には影響しない。
- **macOS・Windows の実機未検証**: 取得物の展開後の配置・ライブラリ名・コード署名(macOS の Gatekeeper)の扱いは、Linux のスパイクで推測できない部分がある。PR で未確認として明記し、利用者の確認を待つ。
- **取得の規模**: 全 VVM で約 1.65 GB。管理画面でサイズを明示し、空き容量の判定(段階1の翻訳と同じ)を通す。
- **性能**: CPU のみの合成が、実用的な速さで終わるかは、スパイクで測る。遅い環境では、キューの上限(段階1)で溢れた分が捨てられる。
- 声ごとのキャラクター規約は、クレジットの表記と各キャラクターの規約へのリンクで足りる前提だが、2026-11-20 時点の `TERMS.txt`では、Nemo を含め、全員が「クレジット表記があれば商用・非商用で利用可能」の同じ条件だった(`雨晴はう` は個別の節がない)。規約が変わったら、上記の写しの更新で再同意になる。
