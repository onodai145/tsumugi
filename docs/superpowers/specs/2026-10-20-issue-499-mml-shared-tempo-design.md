# MML のテンポ共有 `t=` の設計

Issue #499 の「中くらい」の候補のうち、「トラック間のテンポ共有」。関連: `2026-10-15-issue-75-mml-ringtone-design.md`(トラックは独立)、`2026-10-20-issue-499-mml-syntax-extension-design.md`(PR #511。小さい候補 6 つ)。

## 目的

今のトラックは、テンポ・オクターブ・長さ・音量・音色が独立している。テンポを揃えたいときは、全トラックの頭に同じ `t` を書くしかない(ユーザーガイドもそう案内している)。全トラックの初期テンポを 1 回で指定できる記法を足す。

成功条件:

- `t=140` で、全トラックの初期テンポを指定できる。トラックごとの `t<n>` は今までどおり、そのトラックだけを変える。
- 誤りは今までどおり「N 文字目」の位置つきエラーで返る。
- 今まで通っていた MML は、同じ `MmlScore` になる(`t=` は今は構文エラーなので、保存済みの MML の意味は変わらない)。
- `NoteEvent` / `MmlScore` / `MmlError` / `tauri.gen.ts` / レンダラー(`mmlRender.ts`)は変えない。

## 範囲

含める: `t=<n>`(初期テンポの共有)と、それに伴うフロントの追随(字句解析・「記法」ヘルプ・ユーザーガイド)。

含めない:
- 曲の途中のテンポ変化を全トラックで同期すること(拍の位置でそろえるテンポマップ)。今のパーサーはトラックを別々に実行しており、構造の変更が大きい。必要になったら別 Issue にする。
- テンポ以外(`o` `l` `v` `q` `@`)の共有。
- 入力補助キーに `=` を足すこと(普通のキーボードで打てる。必要なら後で足す)。

## 原典の確認結果(2026-10-20)

他の MML 方言の「複数トラックのテンポ」の扱いを、README・仕様書・ソースで確かめた。

| 方言 | 確認できた内容 | 出典 |
|---|---|---|
| MCK | テンポ `t` は**チャンネルごと**(「Sets the tempo of a track」、既定 120、範囲 1〜255)。全体テンポは無い。揃えるには、チャンネル見出しに複数を並べて(`ABCDE t150`)、同じ命令を複数のチャンネルへ同時に書く。 | `mckc-e.txt`(Tempo の項)、`mck_guide_v1.0.txt`(Tempo Settings) |
| ffmml(MCK 方言) | テンポはチャンネルごとの `Clocks` が持つ。見出しに複数のチャンネル名を書くと、続く命令が、名前のあるすべてのチャンネルへ複製される。 | `src/channel.rs`(`Channels::parse`)、`src/clocks.rs` |
| sakuramml | `Tempo(n)`(別名 `T` `BPM`、既定 120)は「曲全体に関わる情報」。実装は SMF のテンポのメタイベントを、**そのトラックの現在の時刻**に書く(`song.tempo` も曲単位)。SMF のテンポが全トラック共通かどうかは、ソースではなく MIDI の一般的な仕様に基づく(このリポジトリのソースでは確かめていない)。 | `docs/syntax-meta.md`、`src/runner/cc.rs`(`exec_tempo` / `tempo_change_f64`) |
| tonejs-mml-to-json | `t` は `Transport.bpm.value` を設定する命令になる(ソースのコメントは「Transport settings are global」)。ただし出力にはその時刻が付かず(引数は `[bpm]` だけ)、曲の途中・複数トラックでどう効くかは、このソースだけでは確かめられていない。 | `rust/src/ast2json.rs`(`AstToken::Tempo`) |
| mml-iterator | `t`(既定 120)。トラックの概念は README に無い(1 つの文字列を 1 つの列として読む)。 | README |

分かったこと:
- MCK と ffmml は、tsumugi と同じく**テンポはトラックごと**で、揃えるための仕組みは「複数のトラックへ同じ命令を書く」(全体のテンポ記法ではない)。`t=140` の効果(全トラックの初期テンポを 1 回で指定する)は、MCK の `ABCDE t150` と同じで、書き方だけが違う。
- sakuramml は、テンポが曲全体のもの(SMF のテンポ)。曲の途中のテンポ変化が全トラックに効く方式は、この spec で「含めない」とした範囲(テンポマップ)にあたる。
- どの方言も、`t=` という書き方はしない。`t=` は tsumugi の独自の記法で、互換を目的にしない。

## 決定

| 項目 | 決定 | 理由 |
|---|---|---|
| 共有の範囲 | 初期テンポだけ | 途中のテンポ変化の同期は、トラックを別々に実行する今の構造を変える大きな変更になる。 |
| 記法 | `t=<n>`(`n` は 32〜255、`t` と同じ) | `t=` は今は構文エラーで、保存済みの MML の意味が変わらない。色分けも実装も最小で済む。 |
| 置ける場所 | トラックの最初の音符・休符(`^` を含む)より前で、`[ ]` と `{ }` の外。どのトラックでもよい | 宣言であって「そこからテンポが変わる」ものではない。途中に書けるようにすると、後者と誤解しやすい。ループの中に置くと展開で複数になる。 |
| 個数 | 1 回だけ。2 個目は、その位置でエラー | どちらが効くかを考えなくて済む。 |
| トラックの `t<n>` との関係 | トラックの `t<n>` が、そのトラックでは共有の値を上書きする | 今までのトラックごとの指定を、そのまま使える。 |

## 構文と意味

| 書き方 | 意味 |
|---|---|
| `t=140` | 全トラックの初期テンポを 140 にする。大文字・空白は今までどおり(`T = 140` も可)。 |
| (書かない) | 初期テンポは 120(今までどおり)。 |
| `t=140` と、トラック内の `t100` | そのトラックは、`t100` を実行した時点から 100。それまでは 140(共有)。トラックの最初の音符より前の `t100` なら、最初から 100。 |

誤りと位置(いずれも 0 始まりの文字位置で、エラー表示は 1 始まりの「N 文字目」):

| 入力の例 | エラー位置 | 内容 |
|---|---|---|
| `t=` の後に数字が無い(`t= c`) | `t` | `t=` の後に数値が必要です |
| `t=31` / `t=256` | 数字の先頭 | テンポは 32〜255 です |
| `c t=140`(音符・休符・`^` の後) | `t` | `t=` はトラックの最初の音符・休符より前に書いてください |
| `[t=140 c]2` / `{t=140 c}4` | `t` | `t=` は繰り返し・連符の外に書いてください |
| `t=140 c ; t=100 d`(2 個目) | 2 個目の `t` | `t=` は 1 回だけ書けます |

注意点(ユーザーガイドにも書く):
- `t=140` だけのトラック(`t=140 ; c ; d`)は、今の `t120` だけのトラックと同じく、**トラックとして数えられる**(上限の 4 に含まれ、レンダラーはトラック数で音量を下げる)。普通は、最初のトラックの頭に書く(`t=140 c d e ; o3 c g`)。

## 設計

Rust は `src-tauri/src/mml.rs` だけを変える。

- `Op::SharedTempo(u32)` を足す。`parse_track` の `'t'` で、次の文字が `=` なら共有テンポとして読む(位置と範囲の検査は上の表のとおり)。「最初の音符・休符より前」は、そのトラックの `out` に `Note` / `Rest` / `TieLen` がまだ無いことで判定する。「繰り返し・連符の外」は、スタックが空であることで判定する。
- `parse` を 2 段にする。(1) 全トラックを `parse_track` する(トラック数の上限の検査は、今と同じく各トラックの前に行う)。(2) 各トラックの `SharedTempo` を集めて 1 つに決める(2 個目はエラー)。(3) 各トラックを `run_track` する。`run_track` には初期テンポを引数で渡し、`SharedTempo` の命令は何もしない。
- 副作用: 複数のエラーを持つ入力で、後ろのトラックの構文エラーが、前のトラックの実行時エラー(90 秒超過・音数超過)より先に報告される。エラーが 1 つだけの入力には影響しない。

フロント:
- `lib/mmlLexer.ts`: `t` の直後が `=`(空白を除いて)なら、`t=` を 1 つのコマンドトークンにする(`v+` と同じ扱い)。数字は `number`。
- `ui/settings/SoundChoicePicker.svelte` の「記法」ヘルプに 1 行足す。
- `docs/guide/user-guide.md`: 記法の表に 1 行足し、「テンポを揃えたいときは各トラックに `t` を書いてください」の文を、`t=` を案内する文に直す。

## テスト

- Rust(`mml.rs`): 共有が全トラックの初期テンポに効くこと(音の開始・長さ)、トラックの `t<n>` が上書きすること(先頭と途中)、`t=` が無ければ 120 のままであること、`t=` を 2 本目に書いても全トラックに効くこと、`t=` だけのトラックがトラックに数えられること。誤り(上の表の各行)の位置。`t=` を含まない既存のテストが全部そのまま通ること。
- フロント(Vitest): `mmlLexer` の `t=`(空白・大文字を含む)、`SoundChoicePicker` のヘルプに `t=` が出ること。
- 実機(手動): Xvfb と隔離したインスタンスで、`t=` を含む MML の入力・色分け・エラー表示・試聴(`play_notify_sound` に渡る値)を確認する。音が鳴ることは確認できない(Xvfb に音声デバイスが無い)。

## 未確認・リスク

- 他方言との互換は目的にしていない(「原典の確認結果」を参照)。tonejs-mml-to-json の `t` が、曲の途中・複数トラックでどう効くかは、ソースだけでは確かめられていない。
- 全トラックを先に構文解析するため、4 トラックそれぞれが展開上限(50 万命令)に近いと、4 本分の命令が同時にメモリに載る(今までは 1 本ずつ)。時間はテストで見るが、メモリのピークは測らない(実装後の確認に「未確認」と書く)。
- エラーの報告順の変更(上記の副作用)が、既存のテストに影響しないことは、実装時に確かめる。
- 「`t=` だけのトラックがトラックに数えられる」ことは、書き方を知らない人が音量の低下に気づきにくい。ガイドの注意書きで補う。気になるなら、`t=` だけのトラックを数えない変更を別に検討する(今の `t` だけのトラックの扱いも変わるので、この spec では行わない)。

## 実装後の確認

2026-10-20、`feat/issue-499-mml-shared-tempo` の HEAD db61f29 で確認した。実アプリは Xvfb(:97)・`dbus-run-session`・隔離した XDG_*(/tmp 直下)で起動し、`WAYLAND_DISPLAY` は unset した(実画面には出していない)。設定にはダミーのアカウント(`misskey.invalid`)だけを書いた。フロントは、ユーザーの開発インスタンスの vite(127.0.0.1:5173、作業ツリーを配信)を読み込み、バイナリは同じ作業ツリーの `target/debug/tsumugi`(新しいエラー文言が入っていることを確認)を直接起動した。入力は xdotool による実際のキー入力。

確認できたこと:
- 自動テスト: `cargo test` は 770 passed / 0 failed / 61 ignored(`mml::` は 72 件)、`pnpm check` は 0 errors(既存の `UrlPreviewCard.svelte` の警告 1 件のみ)、`pnpm test` は 97 files / 1039 tests passed。`git status` は空で、`tauri.gen.ts` は変わっていない。
- `rustfmt --check src/mml.rs`: 差分は 5 箇所で、すべて `main` にも既にある(増えていない)。
- 4 トラックがそれぞれ展開上限に近い入力(`four_tracks_at_the_expansion_cap_parse_quickly`、各トラック約 49.5 万命令): 0.11 秒(debug のテストビルド)。
- 実アプリ(隔離インスタンス。設定→通知で「通知音を鳴らす」ON、種類「MML（打ち込み）」):
  1. `t=60 c4 d4 ; e4 f4`: 構文エラーなし、「再生時間 2.0 秒」、文字 18/5000・音 4/3000・トラック 2/4。`t=` がコマンドとして色分けされた(`.mml-command` に `t=`)。
  2. `t=60 ` を消した `c4 d4 ; e4 f4`: 「再生時間 1.0 秒」(共有を書かなければ今までどおり 120)。
  3. `c4 t=140`: 「4 文字目: `t=` はトラックの最初の音符・休符より前に書いてください」(赤字)。試聴・保存は `disabled`。`t` に波線が付き、「4 文字目」を押すとカーソルが `t` の手前(添字 3)に移った。
  4. `[t=140 c]2`(2 文字目、繰り返し・連符の外に書いてください)、`t=140 c ; t=100 d`(11 文字目、1 回だけ書けます)で、それぞれ位置つきのエラーが出て、保存・試聴が `disabled` になった。
  5. 「記法」に、`t=140 全トラックの初期テンポ(最初の音符より前に 1 回だけ。トラックごとの t で上書き)` の行が出た。
  6. 試聴: `fetch` の `ipc://` を記録した。`parse_mml` の後に `play_notify_sound` が呼ばれ、`choice` は `data:audio/wav;base64,UklGR…`(152,975 文字)。WAV の大きさは 114,704 バイトで、22050Hz・16bit・モノラルの約 2.6 秒分(再生時間 2.0 秒 + 末尾の 0.6 秒)と整合する。「試聴に失敗しました」は出ず、ログに WARN / ERROR / panic はなかった。

確認できなかったこと:
- 実際に音が鳴ること、聞こえ方(Xvfb に音声デバイスが無い)。共有したテンポでトラックが揃って鳴るかは、耳では確かめていない(開始・長さの値はテストで確認した)。
- 4 トラックが展開上限に近いときのメモリのピーク(時間だけを測った)。
- 保存と再起動後の復元(今回は確認していない。保存の経路は `t=` に依存しない)。
- Android の実機・エミュレーター、macOS / Windows。
