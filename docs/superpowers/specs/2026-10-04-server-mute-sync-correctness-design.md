# サーバー側ミュート同期の正しさ 設計 (Issue #456 P2)

サーバー側ミュートの同期(`sync_server_mutes`)について、#454 / PR #455 の最終レビューで残った3点を直す。

1. 正規表現ルールの `i` フラグだけを外した変更を、解除として検出できない。
2. 同じアカウントの同期が並行すると、保存値の「読み出し → 比較 → 書き込み」が競合する。
3. 不正な正規表現のルールが `parse_muted_words` で黙って落とされると、ルールが消えたように見えて、境界が不必要に捨てられる。

設計: `docs/superpowers/specs/2026-10-03-server-mute-boundary-design.md`(#454)の続き。同 spec の「既知の制限」(`i` フラグ)と「後続の候補」の一部を、本設計で置き換える。

## 背景・原因

### キーが、パース後のルールから作られている

#454 は、同期のたびにミュートの集合を `ServerMuteSnapshot`(`users` と `words`)として保存し、前回にあって今回に無い要素を「解除」として検出する。`words` の要素は、`WordMuteRule::key()` が作る文字列で、パース後のルールから導く。

- `Regex(re)` のキーは `r:` + `re.as_str()`。`i` フラグは `RegexBuilder::case_insensitive` で適用されるので、`as_str()` に残らない。`/x/i` を `/x/` に変えても(一致が減る=解除)、キーが同じで、検出できない。
- 不正な正規表現(フラグの文字が不正、またはコンパイル失敗)は、`parse_word_element` が `None` を返して捨てる。キーも作られない。前回は妥当で今回は不正になったルール(サーバーで編集された、など)が、解除に見える。

どちらも、キーを「パース後」ではなく「サーバーから来た要素そのもの」から作れば消える。

### 同じアカウントの同期が、直列化されていない

`sync_server_mutes_core` は、取得 → メモリ上の集合の差し替え → 保存値の読み出し → 比較 → 境界の破棄 → 保存値の書き込み、を行う。同じアカウントの2回の同期(起動時の同期とアカウント再認証など)が重なると、一方が読んだ保存値を、他方が更新した後で、古い比較結果で上書きしうる。害は、次回に余計に境界を捨てるだけ(安全側)で、解除は見逃さない。ただし、無駄な境界の破棄と、保存値の振動を避けられる。

## スコープ

- 対象: 上記3点。
- 対象外:
  - 定期同期(#456 の P4)。
  - 境界の破棄(DB)が失敗したとき、保存値を更新しないことのテスト、`sync_server_mutes` のラッパのテスト(#456 の P3)。
  - アカウント削除時の保存値の掃除(#456 の P1 で対応済み)。
  - DB スキーマ、Tauri コマンドの署名、TS バインディング、フロントエンド、設定 JSON の形。

## 設計

### キーの作り方(`src-tauri/src/api/mutes.rs`)

`/i` の生 JSON の `mutedWords` を1パスで読んで、要素ごとに次を返す純粋関数を足す。

```rust
pub(crate) struct MutedWordEntry {
    /// 適用するルール。不正な正規表現では `None`。
    pub rule: Option<WordMuteRule>,
    /// サーバー側の要素を表す安定した文字列(スナップショットのキー)。
    pub key: String,
}
```

要素ごとの扱い(現在の `parse_muted_words` / `parse_word_element` と同じ分岐):

| 要素 | 条件 | `rule` | `key` |
|---|---|---|---|
| 配列 | 語を trim して空語を除く。全滅 | (要素なし) | (要素なし) |
| 配列 | 1語以上残る | `Words(語群)` | `w:` + 語を小文字にしてソートし `\u{1f}` で連結 |
| 文字列(`/pattern/flags` 構文ではない) | trim して空 | (要素なし) | (要素なし) |
| 文字列(同上) | 空でない | `Words(vec![語])` | 1語の配列と同じ `w:` 形式 |
| 文字列(`/pattern/flags` 構文) | フラグが妥当で、コンパイルも通る | `Regex(re)` | `r:` + 要素の文字列そのまま(`/pattern/flags`) |
| 文字列(同上) | フラグが不正、またはコンパイル失敗 | `None`(警告ログは現状どおり) | `r:` + 要素の文字列そのまま |

- `w:` のキーは、現在の `WordMuteRule::key()` と**同じ**文字列。`r:` のキーだけが変わる(`r:{pattern}` → `r:/{pattern}/{flags}`)。
- `fetch_muted_words` は、`{ rules: Vec<WordMuteRule>, keys: Vec<String> }` を返す。`parse_muted_words`(ルールだけを返す)は、同じ関数の薄いラッパとして残す。既存のテストは、変えずに通る。
- `WordMuteRule::key()`(`src-tauri/src/filter/mute.rs`)は、使われなくなるので削除する。テスト4件は、キーを作る関数のテストへ移す。`WordMuteRule` の型は変えない。

結果の振る舞い:

- `i` フラグだけを外す(`/x/i` → `/x/`): `r:/x/i` が消え、`r:/x/` が増える。解除として検出される。
- `g` など、適用しないフラグの変更(`/x/g` → `/x/`)も、解除と見なす。必要以上に境界を捨てるだけで、安全側。
- 不正な正規表現が、前回も今回もサーバーに残っている: キーが残るので、解除に見えない。境界は捨てない。
- 妥当だった正規表現が、サーバーで編集されて不正になった(または別のパターンに変わった): 古いキーが消えるので、解除として扱う(編集の一般則どおり、安全側)。

### アップグレード時の挙動

保存済みのスナップショットの正規表現キーは、旧形式(`r:{pattern}`)。新しい形式(`r:/{pattern}/{flags}`)とは一致しないので、正規表現のワードミュートを持つアカウントは、アップグレード後の初回同期で、旧キーが消えたように見え、境界が1回捨てられる。`w:` のキーは変わらないので、語だけのアカウントには影響しない。捨てるのは安全側(次の backfill が API 経由になるだけ)なので、移行処理は書かない。

### 同期の直列化(`src-tauri/src/state.rs`、`commands/mute.rs`、`commands/account.rs`)

- `AppState` に `server_mute_sync_locks: Mutex<HashMap<String, Arc<tokio::sync::Mutex<()>>>>` を足し、アカウントごとのロックを、必要になったときに作る。
  - `server_mute_sync_lock(&self, account_id) -> Arc<tokio::sync::Mutex<()>>`
  - `forget_server_mute_sync_lock(&self, account_id)`(`remove_account` が、他の `forget_*` と同じ並びで呼ぶ)
- `sync_server_mutes_core` は、**冒頭(取得より前)** でそのアカウントのロックを取り、`reflect_server_mute_change` の終わりまで持つ。これで、取得、メモリ上の集合の差し替え、保存値の読み出し・比較・書き込みが、アカウント内で直列になる。別のアカウントの同期は、並行のまま。
- ロックの順序は「同期ロック → 境界の書きロック(`invalidate_boundaries`)」。境界の書きロックを持ったまま同期ロックを取る経路は無いので、デッドロックしない。
- 取得(ネットワーク)の間もロックを持つので、同じアカウントの2回目の同期は、1回目の完了まで待つ。同期は、起動時とアカウント追加・再認証時にしか呼ばれず、通常は重ならないので許容する。タイムアウトは設けない(取得側のタイムアウトに従う)。
- `remove_account` がロックのエントリを消した後も、実行中の同期は `Arc` で持っているので、そのまま完了する。

## 検討した代替案

- **`WordMuteRule::Regex` に元のフラグを持たせる(#456 の提案)**: 型変更で `api/mutes.rs` と `filter/mute.rs` のパターン一致、テストが増える。不正な正規表現の件は別に直す必要がある。キーの形式が変わるので、アップグレード時の1回の破棄は、同じく起きる。生の要素からキーを作る方が、3点を一度に直せ、型を変えずに済む。
- **旧形式のキーを移行する**: 旧 `r:{pattern}` は、`i` が付いていたかを区別できないので、正しく新形式へ移せない。1回の安全側の破棄の方が単純。
- **ロックを取得の後で取る**: 取得した集合の古い・新しいが、ロックの取得順と食い違いうる(後に取得した新しい集合を、先に取得した古い集合が上書きしうる)。取得の前に取る。

## テスト

- キーを作る関数(単体):
  - 語の順序と大文字小文字に依らない。
  - `w:` と `r:` が衝突しない。
  - 通常の文字列は、1語の配列と同じキーになる。
  - `/x/i` と `/x/` でキーが違う。
  - 不正な正規表現(不正なフラグ、コンパイル失敗)は、キーを持ち、`rule` が `None`。
  - 語が全滅した配列・空の文字列は、要素にならない。
  - 1語の中の区切り文字の結合(`"ab"` と `"a","b"`)が区別される(現行テストの移植)。
- `parse_muted_words` の既存テストが、変えずに通る。
- `sync_server_mutes_core` の結合テスト(既存の wiremock の形):
  - 前回 `/x/i`、今回 `/x/` → そのアカウントの境界が空になる。他のアカウントは、そのまま。
  - 前回も今回も、不正な正規表現が残っている → 境界を捨てない。
  - 前回 `/x/i`、今回も `/x/i` → 境界を捨てない。保存値は変わらない。
- 直列化: テスト側が同じアカウントのロックを持ったまま `sync_server_mutes_core` を起動し、短いタイムアウトの間は完了しない(wiremock へのリクエストも0件)ことを確認する。ロックを放すと完了し、リクエストが飛ぶ。別アカウントの同期は、ロックを持たれていても完了する。実装が正しければ必ず通る形で、不安定にならない。
- 変異確認: ロックの取得を外すと、直列化のテストが落ちること。キーを `re.as_str()` ベースに戻すと、`i` フラグのテストが落ちること。

## 影響範囲

- 変更するファイル: `src-tauri/src/api/mutes.rs`、`src-tauri/src/filter/mute.rs`、`src-tauri/src/state.rs`、`src-tauri/src/commands/mute.rs`、`src-tauri/src/commands/account.rs`、`src-tauri/src/store/settings.rs`(`ServerMuteSnapshot.words` のコメントのみ)。
- DB スキーマ、Tauri コマンドの署名、TS バインディング、フロントエンド、設定 JSON の形は変わらない。スナップショットの `words` の要素(文字列)の中身だけが、正規表現ルールで変わる。

## 後続の候補(本設計では扱わない)

- 定期同期(#456 の P4)。本設計の同期ロックが、その前提になる。
- 境界の破棄が失敗したとき保存値を更新しないことのテスト(#456 の P3)。
