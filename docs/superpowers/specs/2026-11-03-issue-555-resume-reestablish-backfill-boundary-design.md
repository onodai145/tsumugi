# 起動時に、キャッシュ有りで境界の無いカラムの backfill 境界を再確定する 設計 (Issue #555)

Issue #228 / #238（`2026-09-30-multi-source-backfill-cache-design.md`）の続き。backfill のキャッシュ優先読み出しは、カラムごとの境界 `column_source_boundary` が全ソース分そろっているときだけ働く。この境界が一度でも失われると、キャッシュが十分にあるカラムでは**二度と作り直されず**、スクロールバックが常に API に落ちる。起動時の復元(`resume_column`)で境界を作り直す。

## 背景: 観測された症状と根拠

「キャッシュ DB に保存されているはずのタブが、スクロールバックで API を叩く」という報告を、稼働中インスタンスで調べた(2026-11-03)。

- 9 カラム中、キャッシュ有りの 7 カラムのうち 6 カラムで `column_source_boundary` の行が 1 つも無かった。行があるのは、キャッシュが空だった `c8c33514` と、片方のソースの行だけが残る `ffc1601a` の 2 つ。
- dev アカウントの素の Hybrid タブ(`ffc01f1c`、キャッシュ 4,568 件、境界なし)を 1 回上へスクロールすると、`backfillCacheFallbackBoundary` が 2 → 3 になり、`notes/hybrid-timeline` が 1 本記録された(`FallbackOther` と `Hit` は増えない)。スクロール後も境界の行は作られなかった。

境界が無いまま固定される理由は、境界を**新規に作る**経路が `open_stream_and_fetch`(初回取得)だけで、これを通るのが次の 3 つに限られるため。

1. `add_column`
2. `update_column`(キャッシュを全消去してから開き直す)
3. `resume_column` で、キャッシュが空(または有効境界で絞って空)のとき

境界を**動かす**経路は、どちらも既存の行を前提にしている。

- API でのスクロールバック後の延長(`plan_boundary_extend`): 既存の行がある場合だけ延ばす。
- ギャップ埋めが打ち切られた後の引き上げ(`plan_boundary_raise_after_gap`): `prev` が空なら何もしない。

したがって、キャッシュ有りのカラムで境界が欠けると、`resume_column` は初回取得を通らず、境界は戻らない。

2026-08-31 のキャッシュ DB バックアップ(旧テーブル `column_fetch_boundary`)と比べると、境界が無い理由は 2 種類に分かれる。

- **元々作られていなかった**: Hybrid タブ(`ffc01f1c`)は、8/31 の時点で既にキャッシュ 1,390 件・境界なしだった。ミュート操作とは無関係で、今回の症状の直接の原因はこちら。
- **後から失われた**: Social タブ(`46158d01`)は、8/31 には境界があり、現在は無い。失われた操作は特定できていない。

境界を失わせる経路は、仕様として既にある(`set_mute` / 設定インポートによる全カラムの破棄、サーバーミュートの解除またはワードルール編集の検出によるアカウント単位の破棄、片方のソースが取得に失敗した初回取得)。これらを変えることは本設計の対象外とする。本設計は、**どちらの理由でも、境界が無ければ再確定する**。欠けているのは、境界を作る経路のほうである。

## 方針

`resume_column` で、キャッシュ有りでも、キャッシュ優先の対象カラムで有効境界が確定していないなら、キャッシュが空のときと同じく `open_stream_and_fetch` で初回取得をやり直す。これにより境界が書き込まれ、以後の起動とスクロールバックはキャッシュ優先経路を使える。

### 判定

`resume_column` の既存の分岐 `notes.is_empty()` に、次の条件を OR で加える。

```
backfill_cache_eligible(resolved) && effective_boundary(...) == None
```

- 有効境界が `None` になるのは、全ソース分の行がそろっていないとき(行が 0 個の場合と、一部だけ欠ける場合の両方)。`restore_boundary` は、対象外のカラムでも `None` を返すので、`backfill_cache_eligible` の判定を別に持つ。
- 通知カラム、`from cache` を含むカラム、Streaming を持たないソースを含むカラムは、従来どおり対象外。
- 有効境界が確定しているカラムは、従来どおりキャッシュ優先で復元する(挙動を変えない)。

### 取得と書き込み

キャッシュが空のときと**同じ経路**(`open_stream_and_fetch`)を使う。

- 初回ページ(最大 `BACKFILL_MAX_PASSES` パス)を取得し、`cacheable` を `column_note` に書き、`plan_boundary_initial` の結果を `replace_fetch_boundaries` で書く。ストリームも同じロックの中で開く。
- カラムのキャッシュは**消さない**(`update_column` との違い)。既存の `column_note` は upsert で残り、取得範囲の外にある古い行は、次回以降のスクロールバックで使える。
- UI に返すのは取得した新しいページ。キャッシュ有りの経路で出していた `ColumnGapFill` は出さない。

### 表示が境界と食い違わないことの確認

境界 `b_i` は取得ページの最古 id、表示は取得ページ(`INITIAL_LIMIT` 件、ウォーターマーク以上)。したがってスクロールバックの `until_id`(表示中の最古)は `b_i` 以上になり、次のスクロールバックは `plan_boundary_extend` の連続性条件(`until_id >= b_i`)を満たして、境界が古い側へ延びる。最新の 20 件が連続して表示されるので、間に穴は生じない。

### 取得に失敗したとき

今日のキャッシュ有りの経路は、オフラインでも起動できる。この性質を失わないために、再確定のための取得が**全ソース成功**にならなければ、**従来のキャッシュ優先経路**(キャッシュを即返し、ストリームを開き、`fill_gap` をバックグラウンドで実行する)にフォールバックする。

- 初回取得(`fetch_and_filter_multi`)は、ソース単位の失敗を握りつぶして、空の成功を返す。そのため `Err` だけを見ても足りない。`source_outcomes` に `Failed` が 1 つでもあれば「失敗」とみなし、何も書かずにフォールバックする。部分的な結果で、キャッシュの表示を置き換えない。
- 取得が一定時間(5 秒)内に終わらないときも「失敗」とみなし、何も書かずにフォールバックする。復元は直列なので、応答しないサーバーが後ろのカラムの表示まで止めないようにするため。
- 取得は全ソース成功でも、フィルタを通るノートが 0 件なら確定しない(何も書かずにフォールバックする)。確定すると、空の一覧と深い境界が残り、見えていたキャッシュ履歴が隠れて、画面が空のままスクロールバックもできなくなる。該当が無い間は、起動のたびに再確定を試みる。
- `Err` のとき(クライアントを作れない、キャッシュ書き込みの失敗など)も、ストリームは開かれていない(いずれも、ストリームを開く前に失敗する)。したがってフォールバックしてもストリームが二重に開かれることはない。
- ただし、**世代の不一致**(取得中に `update_column` / `close_column` が走った)の場合は、フォールバックしてはならない。古い定義でストリームを開いて、リークさせるため。この場合は従来どおり `Err` を返す。判別は `ColumnFence::is_current`(ロックを取らない読み取りの照会)で行い、世代が現行でないときだけ `Err` を返す。これは取得が失敗した(フォールバックに入る)場合にも確認する。エラー文字列の一致で判別しない。
- フォールバック時は、境界が未確定のまま。次の起動でもう一度再確定を試みる。

### メトリクス

`resumeCacheFallback` は「キャッシュが空で REST に落ちた回数」の意味を保つ。再確定の結果を反映して画面に返した回数を、別カウンタ `resumeBoundaryRefetch` に数える(フォールバックしたときは、従来どおり `resumeCacheHit` に数える。`CacheMetrics` と `DebugMetrics` にフィールドを追加し、TS バインディングを再生成する)。これで、再確定が働いたか、一巡したか(0 に戻るか)を実機で確認できる。

## 検討した代替案

### A': キャッシュ表示を維持し、ギャップ埋めの結果から境界を種付けする

起動時の表示と `fill_gap` を変えず、`fill_gap` が `newest_known_id` に追いついたとき、`b_i = newest_known_id` を書く案。起動の遅延が増えないが、**採用しない**。

表示中の最古ノート(キャッシュの新しい 20 件の最古付近)は、`newest_known_id` より古い。スクロールバックの `until_id` が境界より古くなり、`plan_boundary_extend` の連続性条件(`until_id >= b_i`)を満たさない。したがって境界が一度作られても延びず、キャッシュに Hit するのは `E` より新しい狭い範囲だけになる。

### A'': 表示はキャッシュのまま、バックグラウンドで初回取得だけ行い境界を書く

A' と同じ理由(表示と境界の食い違い)で採用しない。境界を書くなら、その境界と同じ範囲を画面に出さなければならない。

### B: 境界を失わせる設計を見直す

ミュート変更でカラム全体の境界を破棄せず、取り直しが必要な範囲だけ無効にする。根本的だが、影響範囲が広い(`mute.rs`、境界のスキーマ、フェンスの世代管理)。本設計の対象外とし、別の課題として扱う。今回観測した Hybrid タブ(元々作られていなかった)とは無関係で、「後から失われた」ケースの再発を減らすためのもの。必要かどうかは、本設計の後に改めて判断する。

## 制約とリスク

- **起動の遅延(初回のみ)**: フロントの復元(`store.svelte.ts` の `for ... await commands.resumeColumn`)はカラムを**直列**に処理する。境界が無いカラムが N 個あると、その N 個が REST の往復(数百 ms〜1 秒強)を順番に待つ。再確定が済んだカラムは、次の起動からキャッシュ優先に戻る。強いフィルタのカラムは最大 5 パスかかる。
- **表示の変化**: 再確定の起動では、そのカラムの先頭は、取得した最新 20 件になる。閉じていた間にたまった分を `fill_gap` が先読みして表示(最大 `gap_fill_limit` 件)する挙動は、この起動に限り行われない。たまった分には、スクロールバックで到達できる。
- **再確定が繰り返される場合**: 取得に失敗し続けるソースを含むカラムは、境界がそろわず、起動のたびに再確定を試みて失敗し、キャッシュ表示にフォールバックする(表示は変わらず、無駄な取得が起動ごとに増える)。現状は全ソースが REST 対応なので起きにくい(Issue #429)。
- **起動後に境界を失った場合**: 起動中にミュート変更などで境界が破棄されると、次の起動まで再確定されない(その間のスクロールバックは API)。本設計では扱わない。必要なら B の領域。

## 未確認の事項

- `ffc1601a`(`from home, local`)で、`source_idx = 0` の行だけが欠けている理由。`plan_boundary_raise_after_gap` が「1 ページも取れていないソースの行を落とす」処理によるものと推測しているが、確認していない。本設計の再確定で修復されるはずだが、同じカラムで再発するかは実機で確認する。
- 機能導入前から境界が無かったカラムが、旧スキーマからの移行(`source_idx = 0` へのコピー)で何件引き継がれたか。

## テスト

実装計画で詳細を決める。少なくとも次を、`commands/column.rs` の既存のテスト(`open_stream_and_fetch_*`、wiremock)に倣って追加する。

- 判定: キャッシュ有り + 対象 + 有効境界なし → 再確定。有効境界あり → 再確定しない。一部のソースの行だけ欠ける → 再確定。通知 / `from cache` / Streaming なしのソース → 再確定しない。
- 再確定の取得が成功すると、境界が全ソース分書かれ、既存の `column_note` が消えない。
- 全ソースの取得が失敗すると、従来のキャッシュ優先経路にフォールバックする(キャッシュを返し、ストリームを開く)。
- 複数ソースのうち一部だけ失敗しても、何も書かずにフォールバックする(部分的な結果で表示を置き換えない)。
- 世代の不一致では、フォールバックせず `Err` を返す(ストリームも開かない)。
- `resumeBoundaryRefetch` が再確定のときだけ増える。

## 実機での確認

`reference-verify-cache-metrics-via-debug-bridge` の手順(Debug Bridge で稼働中インスタンスのメトリクスを読み、境界は読み取り専用コピーで確認する)で行う。隔離インスタンスではなく実データを使うので、**ブランチを切ってから**、ホットリビルドされる点に注意する(キャッシュ DB のスキーマは変えない)。

1. 再起動後、`resumeBoundaryRefetch` が、境界の無い対象カラムの数だけ増える。
2. `column_source_boundary` に、対象の全カラムの行がそろう。
3. 2 回目の起動で `resumeBoundaryRefetch` が 0 のまま。
4. Hybrid タブを上へスクロールして、`backfillCacheHit` が増え、`notes/hybrid-timeline` が記録されない。
