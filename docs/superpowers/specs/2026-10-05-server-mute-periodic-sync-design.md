# サーバー側ミュートの定期同期 設計 (Issue #456 P4)

Web 側(Misskey のサーバー)でミュートやワードミュートを変更しても、tsumugi には、次の起動か再認証まで反映されない。定期的に同期して、反映の遅れを数時間に抑える。#454 / PR #455(解除の検出)の最終レビューで「後続の候補」とした項目。

## 背景

`sync_server_mutes`(Tauri コマンド)は、起動時(カラムの復元より前)と、アカウント追加・再認証時にだけ、フロントから呼ばれる(`frontend/src/lib/store.svelte.ts` の `#syncServerMutes`)。定期的には呼ばれない。

- ミュートの**解除**を Web 側で行うと、次の起動まで、キャッシュ優先の backfill が、解除したユーザーのノートを欠いたまま「完全」として返しうる(#454)。解除の検出と、そのアカウントのカラムの境界の破棄は、P2 までに実装済みだが、同期が走らなければ働かない。
- ミュートの**追加**も、次の起動まで、受信するノートに効かない。

Rust 側は、すでに次が揃っている。

- 同期の本体(`sync_server_mutes_core`)。解除の検出と境界の破棄(#454)、同じアカウントの同期の直列化(P2、アカウント単位のロック)。
- 取得中の書き込みと境界の破棄の競合を防ぐフェンス(#446 / #452)。

したがって、定期同期は、**フロントのタイマーが、同じコマンドを定期的に呼ぶだけ**で実現できる。

## スコープ

- 対象: フロントの定期同期のタイマー。
- 対象外:
  - 同期間隔の設定化(下記「判断」参照)。
  - ウィンドウのフォーカスや可視性に応じた同期。
  - Rust 側のスケジューラ。
  - 表示済みノートの再フィルタ(下記「挙動」参照)。
  - ユーザーガイド(サーバー側ミュートの同期は、記載が無い。ローカルの NG だけが書かれている)。
  - Tauri コマンドの署名、TS バインディング、Rust 側のコード、DB スキーマ。

## 設計

変更は `frontend/src/lib/store.svelte.ts` の中だけ。

- 定数 `SERVER_MUTE_SYNC_INTERVAL_MS = 6 * 60 * 60 * 1000`(6時間)。既存の `PRUNE_INTERVAL_MS`(キャッシュ間引き、6時間)と揃える。新バージョン確認は4時間。
- フィールド `#serverMuteSyncTimer: ReturnType<typeof setInterval> | null = null`。
- `boot()` で、既存のタイマー(`#statsTimer`、`#updateCheckTimer`、`#pruneTimer`、`#clockTimer`)の並びに、`boot()` が再実行されても多重にならないよう、先に解除してから張る(既存のタイマーと同じ書き方)。タイマーは、`boot()` の末尾で張る。起動時の同期は、これまでどおり、`boot()` の前半(カラムの復元前)で行い、その直後に重ねて走らせない。
- タイマーの1回ごとに、**その時点の** `this.accounts` の全アカウントで、`#syncServerMutes(account.id, { quiet: true })` を並行して呼ぶ(`Promise.all`)。アカウントの追加・削除に追従する。
- `#syncServerMutes(accountId, options?: { quiet?: boolean })`: `quiet` のときは、成功時のログ(「サーバのミュート/ブロックを同期: …」)を出さない。失敗の警告(権限不足なら「再認証してください」を含む。それ以外は「サーバミュート同期に失敗」)は、これまでどおり出す。定期実行で、Backstage のログが、成功の度に埋まるのを避けるため。
- `teardown()` で、`#serverMuteSyncTimer` を解除する(既存のタイマーと同じ)。

### 判断: 間隔は6時間、設定にしない

- ミュートは、めったに変更しない。起動時にも同期する。反映の遅れが数時間でも、困らない(解除の見逃しの害は、キャッシュ優先の backfill が欠けたノートを返すことで、すぐには気づかない程度)。
- 1回の同期は、アカウントごとに最低3リクエスト(`/i`、`mute/list`、`blocking/list`。ミュートが100件を超えれば、ページが増える)。6時間間隔なら、1日4回で、負荷は無視できる。
- 既存の定期処理(新バージョン確認、キャッシュ間引き)も、固定の定数で、設定項目ではない。必要になったら、設定に昇格できる。
- 代案: 30分。ミュートの変更頻度に対して、短すぎる(ユーザーの指摘で、6時間に変更した)。

### 挙動

- **解除**: 同期で検出され、そのアカウントのカラムの境界が捨てられる(P2 までに実装済み)。次の backfill は、API 経由になる。
- **追加**: 同期の後に、受信・取得するノートから効く。**すでに表示済みのノートは、再読み込みまで残る**。起動時の同期は、カラムの復元前に済むので、この違いは、定期同期でだけ生じる。ローカルの NG(`set_mute`)は、保存時に、表示中のノートからも取り除く(フロントの `setMute`)が、サーバー側ミュートの同期は、そうしない。範囲外とする(同期の結果は、件数だけで、変わったノートの一覧を持たないため)。
- **オフライン・失敗**: `#syncServerMutes` が、警告ログを出して、次の周期まで待つ。リトライはしない。
- **同期の重なり**: 再認証による同期や、起動時の同期と重なっても、P2 のアカウント単位のロックが直列にする。

## 検討した代替案

- **Rust 側のスケジューラ(`tokio` の `interval` を `setup` で起動)**: 認証済みのアカウントの列挙、アカウントの追加・削除への追従、停止(`teardown`)を、新たに作る必要がある。フロントには、同じ作りの先例(新バージョン確認、キャッシュ間引き)があり、`this.accounts` を参照できる。フロントのタイマーが、変更が小さい。
- **ウィンドウがフォーカスされたときに同期する**: 実装が増え、フォーカスの度に通信が走る。ミュートの変更頻度に見合わない。
- **ストリーミング(push)で、変更を受け取る**: Misskey のソース(`misskey-dev/misskey` の `develop`)で確認した。
  - ワードミュート: `i/update`(`packages/backend/src/server/api/endpoints/i/update.ts`)が、更新後に `main` ストリームへ `meUpdated`(`MeDetailed`。`mutedWords` を含む)を流す(`GlobalEventService.ts` の `MainEventTypes`)。公式ドキュメント(`misskey-hub.net` の `main` チャンネルのページ)は、`meUpdated` を載せていない(古いと見られる)。
  - ユーザーのミュート/ブロック: `mute` / `unmute` / `blockingCreated` / `blockingDeleted` は、サーバー内部のイベント(`InternalEventTypes`)で、クライアント向けには流れない。
  - したがって、push だけでは、ユーザーのミュート/ブロックの変更を受け取れず、ポーリングが必要。push で補えるのは、ワードミュートの反映を早めることだけ。`meUpdated` を受けるには、アカウントごとに `main` を購読し続ける必要がある(いまは、通知カラムのあるアカウントだけが `main` を購読する。`stream/connection.rs`)。`meUpdated` はプロフィールの更新の度に飛ぶので、受けるたびに同期が走る。`stream/connection.rs` と購読の変更が要るので、最適化として、後続の候補にする。
  - 確認の限界: ソースは、ページの要約を取得して確認した(原文を直接は読んでいない)。`develop` ブランチの内容で、使っているインスタンスのバージョンや、互換の別実装(Sharkey など)で同じかは、確認していない。リポジトリの OpenAPI スナップショット(`2025.4.1-io.12b`)の `MeDetailed` に、`mutedWords` が含まれることは確認した。
- **ETag などの条件付きリクエストで、変更が無ければ省く**: 6時間間隔の通信量なら、省く必要が無い(対応の有無も、調べていない)。

## テスト

Vitest。既存の `boot()` とフェイクタイマーのテスト(`store.svelte.test.ts` の「boot()後、5秒ごとにnowが更新される」など)の作りに合わせる。実装を外すと落ちることを、変異確認する。

- `boot()` の後、6時間が経つと、全アカウントで `sync_server_mutes` が、もう一度呼ばれる(起動時の呼び出しの後)。
- 定期実行は、成功しても、同期のログを出さない。起動時の同期は、これまでどおり、ログを出す。
- 定期実行の失敗(`sync_server_mutes` が失敗)は、警告ログを出す。
- `teardown()` の後は、時間が経っても、呼ばれない。
- タイマーの発火時に、`boot()` の後に追加したアカウントも対象になり、削除したアカウントは対象外になる。
- 変異確認: タイマーを張らない / `quiet` を無視する / `teardown()` で解除しない / 発火時に `boot()` 時点のアカウントの写しを使う、のそれぞれで、狙いのテストが落ちる。

## 影響範囲

- 変更するファイル: `frontend/src/lib/store.svelte.ts`、`frontend/src/lib/store.svelte.test.ts`。
- Rust 側、Tauri コマンドの署名、TS バインディング、DB スキーマ、ユーザーガイドは変わらない。
